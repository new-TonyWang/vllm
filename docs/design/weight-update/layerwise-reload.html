第二次跑管道：
layerwise reload 的五阶段与三起事故

RL 训练每一步都要把新权重灌进正在服务的引擎。新权重是 checkpoint 格式，引擎显存里躺的是 kernel 格式——所以必须把 PWAL 管道再跑一遍。reload/layerwise.py 的做法是数着元素：一层收齐就立刻处理一层，处理完把结果拷回旧地址。

区别只有一个：这次已经有人握着旧张量的地址了（CUDA Graph）。就是这一个区别，制造了三起事故。本文先讲五阶段和两条通道的编排机制，再用三个真实案例展示它的缺陷——只保地址，不保语义。

第二部分

第二次跑：同一条管道，换一个时刻

RL 训练每一步都要把新权重灌进正在服务的引擎。新权重是 checkpoint 格式，引擎显存里躺的是 kernel 格式——所以必须把第一部分那条管道再跑一遍。区别只有一个：这次已经有人握着旧张量的地址了（CUDA graph）。就是这一个区别，制造了三起事故。

第四章

layerwise reload 的五阶段与两条通道

为什么不能「收齐全部权重再统一跑一遍 pwal」？因为那样显存里要同时装下旧的 kernel 权重和全部层的新 checkpoint 权重。reload/layerwise.py 的做法是数着元素：一层收齐就立刻处理一层，处理完把结果拷回旧地址。

4.1 计数：用 metadata 判断「这层到齐了没有」

整套机制的触发条件不是「收到了哪些名字」，而是数元素个数。包装器每次被调用都做同一套记账（make_online_process_loader，:171）：

# 每次 loader 被调用都重算 total —— 因为层可能晚注册参数（比如 bias） info.load_numel_total = get_layer_size(layer) # 该层应收多少 info.session_expected_numel = get_required_layer_size(layer) _wrap_parameters_weight_loader(layer) # 顺手包装晚到的参数 # 绑定并规范化这次加载的实参 bound_args = loader_signature.bind(*args, **kwargs) # :205 bound_args.apply_defaults() # 缓存这次加载（推迟写入），并累加进度 info.loaded_weights.append((param_name, bound_args)) # :209 num_loaded, ret = get_numel_loaded(original_loader, bound_args) # :211 info.load_numel += num_loaded # :212 info.session_complete = info.session_loaded_numel >= info.session_expected_numel

这段就是第二部分事故 B 里那道防线 ①的实体：load_numel_total 不是算一次就定下来的，而是每次 loader 被调用都重算，并顺手包装那些「层在 __init__ 后期才注册」的参数。源码注释原话是 “layers may register parameters later (e.g., bias)”。

但这套计数有一个已知的软肋，注释里自己写了。有些 qconfig 会把同一个权重加载多次——例如 CT_WNA16 为 qkv 的每个分片各加载一次 weight_shape。于是 load_numel 会冲过 load_numel_total，在层已经处理完之后还继续收到加载调用。现状的兜底是 if not info.can_load(): return + 一条 debug 日志（“Excessive loading”），并依赖一个前提：不可能在没加载完必要权重的情况下先达到 load_numel_total。weight_shape 很小，所以目前安全——但这是个约定，不是保证。
为什么必须「拷回」而不是「换掉」：CUDA graph 捕获时记录的是张量地址。换对象 = 图重放时访问野指针。所以 reload 的定稿动作被硬性限制成 copy_() 到同一块存储——这正是第三章 prefer_copy 那个时间轴的另一半。

4.2 两条通道：管辖 vs 豁免

并非所有张量都进这套记账机制。reload/meta.py:25 有一份按名字精确匹配的豁免名单 SKIP_TENSORS，名单里的张量完全退出管道。先定义活张量：层上当前注册着的那一个——forward 读它，CUDA graph 捕获的也是它的地址。

管辖通道 · 先暂存，后结算
名单外的全部张量：weight、scale …
  1. 张量到达 → 包装器接管：元素数计入 load_numel，加载参数缓存进 loaded_weights。真正的写入被推迟。
  2. 该层收齐 → 物化新张量 → 重放缓存的加载 → 跑 pwal（量化 / permute / repack）。
  3. copy_() 把加工结果拷回活张量的旧地址。
换来两件事：值在进入 runtime 之前有一次被加工的机会；引擎全程记账，知道谁来了、谁没来。
豁免通道 · 一步到位
SKIP_TENSORS 名单内：_expert_map、e_score_correction_bias …
  1. loader 从不被包装。张量到达的那一刻，原始 weight_loader 立即执行 param.copy_(loaded)——源头是传输流，目的地就是活张量本身。
  2. 没有第 2、3 步：不计数、不缓存、不重放、不拷回。
代价是两件事永远做不了：① 到齐核查——漏发只能静默；② 加载后加工——如果某个 kernel 要求换布局，豁免通道给不了。事故 B 就是撞在第 ② 条上。
名单里现在有什么（2026-07 main）：_expert_map、expert_mask、expert_global_to_physical、expert_physical_to_global、expert_local_to_global、e_score_correction_bias——清一色是从不经过 weight loader 的 MoE 路由表。它们本来就不参与「加载」，所以豁免无害。这条共性是判断「什么该进名单」的唯一标准。

Gemma4Router.root_size 是 hidden_size ** -0.5——和 attention 的 1/√d_k 同一个作用，用来压住 router logits 的幅度。它是个派生常量：值完全由 config 决定，训练不改它，checkpoint 里也没有它。所以 vLLM 用 register_buffer(..., persistent=False) 注册它——是张量（能跟着 module 上 GPU、对 torch.compile 友好），但不进 state_dict、永远不会被 weight loader 加载。

正常加载下这一切成立。但 reload 不走 __init__，它走第四章那五步：整层退回 meta → 物化 → 重放 loader。于是 weight 和 root_size 在第 4 步分道扬镳：

分歧点在 4b → 4c：拷回那一步不区分「这个张量本轮真的收到了新数据」和「这个张量从来不该被加载」，对所有 buffer 一律 copy_()。第二个问题跟在后面——_place_kernel_tensors 重新注册 buffer 时用的是 register_buffer(name, buffer)，persistent 默认 True，原来的 False 丢了，这个 buffer 从此开始出现在 state_dict() 里。

症状是真的，但归因错了。PR 认为首次加载就会腐蚀 bias（load_numel_total 只算了 weight → weight 一到就提前触发 → 物化覆盖已加载的 bias）。逐行核代码，这条路上有两道现成的防线：

PR 描述的机制代码里的实际情况
total 只算 weight，weight 一到齐就提前触发防线 ①：包装器每次被调用都先重算 total 并补充包装晚注册的参数（layerwise.py:176-181，注释原话 “layers may register parameters later (e.g., bias)”）。weight 到齐时 total 已含 bias
materialize 把所有非 skip 张量重新分配，覆盖已加载的 bias防线 ②：materialize_layer（meta.py:137）只重新分配 is_meta 的张量。首载时 bias 是真实张量，一根手指都不碰
症状：bias 变成未初始化内存 / 全零症状真实，但唯一可复现的路径是 reload 时传输流漏发 bias：计数永远到不了 total → 由 finalize 兜底 → bias 还是 meta → 物化成未初始化显存 → 没人重放 → 照样拷回

把 bias 加进豁免名单确实让症状消失（垃圾值 → 保留旧值）。但它引入了一个更坏的问题，因为它假定了「bias 只被加载，从不被加工」。CUTLASS 路径确实如此；Marlin 不是——prepare_fp8_layer_for_marlin 在量化阶段对 bias 做两步加工：

  • pad：末维补零，从 part_size_n 填到 tile 对齐的 padded_n（改形状）
  • permute：按 32 个输出通道一组 reshape，用固定下标表 scale_perm_single（[0,1,8,9,16,17,24,25, 2,3,10,11,…]）交错重排。和 per-channel scale 共用同一张表——因为 Marlin epilogue 按线程 fragment 的列布局逐通道加 bias，要求 bias 与 scale 的通道顺序一致

所以 Marlin 层的活 bias 不是 checkpoint 布局，而是重排过的 kernel 布局。豁免通道把 raw 值直接怼进去，kernel 就把第 i 个 bias 加到错误的输出通道上。而这在 A100 上不是小众场景：SM80 没有原生 FP8，online FP8 自动 fallback 到 MarlinFP8——恰好就是这个 PR 想修的功能。

修改前每轮 reload 都把 bias「洗回原始布局，再重排一次」，permute 恰好做一次，所以永远对。剪断这个闭环之后有三种结局，取决于权重到达顺序：

情形一 · bias 晚于 weight 到达
weight 收齐触发 pwal 重跑，此刻它拿到的 layer.bias 是上一轮已 permute 过的值 → 再 permute 一次。随后新 bias 以 raw 布局直接 copy 进活张量 → kernel 按 permuted 语义读一块 raw 数据。静默输出错误。
情形二 · size_n 非 tile 对齐
活 bias 始终是 (padded_n,)，checkpoint 的 bias 是 (part_size_n,) → loader 的 copy_ 形状不匹配，或 pwal 里的 shape assert 直接失败。崩溃。
情形三 · bias 恰好先到、且无 padding
raw 值先写入，pwal 随后 permute 的正好是新值 → 侥幸正确。正确与否取决于到达顺序——最难排查的一类 bug。
结论：这个改动用「按名字全局豁免」去修一个「计数 / 收尾时序」问题。它掩盖了症状（垃圾 → 静默陈旧），却踩坏了 Marlin 现成的正确行为。净效果：H100 无害，A100 把原本正确的 reload 变成顺序依赖的静默错误或崩溃。

正确的修法在收尾，不在名单——见第五章。事实上当前 main 的 SKIP_TENSORS 不含 bias，落地的是收尾闸门。

原因在拷回那两行的分工。_copy_and_restore_kernel_tensors 只让字节流过 copy_()；紧接着 _place_kernel_tensors 把旧的 parameter 对象重新注册回层上——新张量的 dtype / shape / stride 被整体丢弃，旧容器的元数据说了算。

# layerwise.py:445 —— 当前 main，parameters 分支至今没有守卫 for name, param in parameters.items(): param.data.copy_(getattr(layer, name)) # ← 无 dtype / shape 语义校验 # 随后 _place_kernel_tensors（:464）： for name, param in parameters.items(): layer.register_parameter(name, param) # ← 装回的是"旧容器"，元数据以它为准

下游 MLA attention 拿这个 scale 去反量化 kv_b_proj、算 W_UV / W_UK_T（第一章讲过的那个顺序依赖）——scale 是垃圾，两个矩阵就是垃圾，输出成乱码。

对比事故 A：buffers 分支在 PR #44371 之后有了两道守卫（是否本轮加载、persistence 是否保留）；parameters 分支一道都没有。Per-tensor FP8 不受影响（scale 是标量，没有不一致的空间）；受影响的是 block 量化 + 有专有布局的 kernel 这个组合。上游已有多个同族报告——#47116（已合并，XPU 上 weight_scale_inv transpose 导致 MLA dequant 损坏）、#45835、#41670、#40822（checkpoint ↔ kernel 格式转换的架构性 RFC）。
第五章

三起事故，一个缺陷

三个案例的模型、量化格式、硬件全不一样，但落点相同：_copy_and_restore_kernel_tensors 和 _place_kernel_tensors。原因是同一件事——第三章那个精心设计的「装回」家族，在 reload 路径上退化成了一次裸的 .data.copy_()：只保地址，不保语义。

A · 拷了不该拷的
对本轮从未收到加载的张量照样执行拷回，把物化出来的垃圾写进保存好的正确值上。
丢失的语义：
「这个张量本轮到过吗」
B · 为了不拷而整体豁免
用按名字豁免绕开拷回，顺带丢掉了必须做的加工——Marlin 的 pad + permute。
丢失的语义：
「这个张量需要被加工吗」
C · 拷了但没带元数据
字节流过 copy_，dtype / shape / stride 留在旧容器里，装回的是旧标签。
丢失的语义：
「这块字节该按什么解释」

换个说法：第三章列出的三条保证是注册可见性、元数据存活、地址稳定。reload 的拷回路径把第三条抬成了硬约束（CUDA graph 要求），代价是把前两条降级成了「碰巧」。replace_parameter 在首载路径上显式迁移 weight_loader、显式处理删除与新增；在 reload 路径上这些判断没有对应物。

5.1 已经落地的：收尾闸门

事故 B 的分析给出的修法是——问题的根在收尾，不在名单：一个本轮从未收到加载、也没有可信初值的 meta 张量，不应该被物化成垃圾再拷回 kernel 存储。这条守卫已经在了，而且做成了 fail-closed：

# reload/layerwise.py:320 —— 谁没收齐，列出来 def get_incomplete_layerwise_reload(model) -> list[tuple[str, int, int]]: # info.session_started and not info.session_complete # and info.session_expected_numel > 0 # distributed/weight_transfer/nccl_engine.py:245（ipc_engine.py:235 同款） incomplete = get_incomplete_layerwise_reload(self.model) if incomplete: raise RuntimeError( "incomplete weight update; refusing to finalize with " f"{len(incomplete)} unresolved layers (sample={incomplete[:10]})" )

这条规则的好处正是它不点名任何张量：bias、scale、buffer——任何漏发的东西都被同一条守卫拦住，Marlin 的正确行为一行都不用动。事故 A 的 buffer 守卫和这条闸门配合，覆盖了「该来没来」这一整类。

5.2 还缺的：拷回时的语义校验

闸门管的是「张量没到」。事故 C 是张量到了、加工也做了，但结果装不进旧容器——闸门看不见它，因为 load_numel 数得满满的。这一类还没有守卫。

缺口的形状很具体：_copy_and_restore_kernel_tensors 的 parameters 分支在 copy_ 之前不检查新旧张量的 dtype / shape 是否一致，_place_kernel_tensors 也不检查它正在装回的旧容器是否还能正确解释这块字节。

同一处该有的判断，其实第三章早就写清楚了：「首载 rebind、重载 copy」不该是布尔默认值，而该是 replace_parameter 自己能感知 reload 状态 + 做兼容性检测的一个判断。把这个判断补进 reload 的拷回路径——不兼容就明确失败而不是静默降级——事故 C 这一类就和事故 A 一样被一条规则收掉。届时 prefer_copy 参数本身都可以消失。
