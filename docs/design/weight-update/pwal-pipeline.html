第一章

四个挂载点：一个固定顺序

加载完权重之后、推理开始之前，model_loader/utils.py:96 里的同名函数跑四个循环。它们不是可选的——跳过任何一个，对应类型的权重就是错误格式，kernel 输出垃圾。

# model_loader/utils.py:96 — 入口函数，四个循环 def process_weights_after_loading(model, model_config, target_device): # ① 量化层：格式转换（transpose, repack, scale 合并, kernel shuffle） for _, module in model.named_modules(): if isinstance(quant_method, QuantizeMethodBase): quant_method.process_weights_after_loading(module) # ② Attention 层：MLA 权重吸收、KV cache scale 定稿 for _, module in model.named_modules(): if is_deferred_attention_layer(module): module.process_weights_after_loading(model_config.dtype) # ③ HPC 模块：派生状态的 float32 拷贝 for _, module in model.named_modules(): if isinstance(module, HpcModule): module.process_weights_after_loading(model) # ④ Model 级：模型自己的后处理 hook if hasattr(model, "process_weights_after_loading"): model.process_weights_after_loading()

四个循环同名不同义——都叫 process_weights_after_loading，但挂在不同的对象上，做完全不同的事。下面逐个展开。

挂载点 ①：量化层（88 个 quant_method 实现）

遍历所有持有 QuantizeMethodBase 的 module，调它的 process_weights_after_loading。这是规模最大的挂载点——88 个实现、137 个 replace_parameter 调用、覆盖全部量化格式。

做什么：把 checkpoint 的存储格式翻译成 kernel 的运行格式。具体操作因量化方案而异——第二章会展开四类变换。几个典型例子：

量化方案做什么为什么
FP8 per-tensor合并 Q/K/V 三个分片的 scale 到一个 max scale → 重量化 → 转置 [N,K]→[K,N]scaled_mm 需要统一 scale + 列主序
FP8 block委派给 kernel 层（DEEPGEMM: scale layout 转换；Triton: no-op）不同后端要求不同的 scale 内存布局
GPTQ / MarlinINT4 bit 重打包 → Marlin tile 重排 → scale permute + padMarlin 用 warp-level shuffle 读权重，需要特定 tile 格式
FP8 MoEkernel format shuffle + _setup_kernel 组装运行时 kernel 对象MoE 的 fused expert 需要特定数据排列 + kernel 初始化
BF16（无量化）MoE: 按后端 shuffle（或 no-op）+ 建 kernel；Dense: passMoE 即使无量化也需要 kernel format 转换

每个实现内部走同一条管道：读取 → 变换 → 装回 → 委派 kernel → MoE 定稿。第二章讲变换的四种类型，第三章讲装回机制。

挂载点 ②：Attention 层（MLA 权重吸收 + KV cache scale）

遍历所有 Attention 层。必须排在 ① 之后——② 的第一步就是反量化 ① 管辖的权重：有些 Attention 层要从一个大矩阵做矩阵分解、推导出派生权重，分解要求 BF16 完整数值，而 checkpoint 里这个矩阵可能是 FP8 存储的，还原回 BF16 依赖 ① 合并/统一后的 scale。① 没跑完 = 用错误的 scale 还原 = 派生权重全错。以 DeepSeek-V3 的 MLA（Multi-head Latent Attention）为例：

# mla_attention.py:1016 — MLA 权重吸收 # 第一步：把 kv_b_proj 从量化格式还原为高精度（BF16） # 这一步依赖 ① 已经把 scale 处理好了 # 如果 ① 没跑：scale 可能还是分片的 → 反量化结果错误 kv_b_proj_weight = get_and_maybe_dequant_weights(self.kv_b_proj) # 第二步：从反量化后的大矩阵里切出两个小矩阵 W_UK, W_UV = kv_b_proj_weight.split([qk_nope_head_dim, v_head_dim], dim=-1) # 第三步：变换形状，让后续矩阵乘法能直接使用 W_UK_T = W_UK.permute(1, 2, 0) # [L,N,P] → [N,P,L] W_UV = W_UV.transpose(0, 1) # [L,N,V] → [N,L,V]

这个挂载点还处理 KV cache scale 定稿（attention.py:580）——把 checkpoint 带的 q/k/v/prob scale 复制到内部 buffer，没带的初始化为 1.0。

挂载点 ③：HPC 模块

目前只有一个实现：HpcRopeNorm（hpc/rope_norm.py:227）。做的事情很简单——把 RMSNorm 权重的 float32 拷贝存一份到自己的 qnorm_weight / knorm_weight 参数上。

为什么单独一个挂载点？因为 HPC 模块的 process_weights_after_loading 接收的是 model（整个模型），不是 layer（单层）。它需要跨层访问其他层的权重。签名不同，不能和 ① ② 混在同一个循环里。

挂载点 ④：Model 级 hook

最后检查模型对象本身有没有 process_weights_after_loading。目前只有一个模型用到：DeepseekV4ForCausalLMROCM（deepseek_v4/amd/model.py:1022）——做 ROCm 上的 AITER B-preshuffle。

这是"逃生口"——当某个后处理逻辑不属于任何一层，而是需要看整个模型时，模型自己可以实现这个 hook。

顺序依赖总结

挂载点对象签名规模依赖
① 量化层quant_method(module)88 个实现无
② AttentionAttentionLayerBase(act_dtype)3 个类依赖 ①（反量化 kv_b_proj 需要已处理的 scale）

四个挂载点，一个原则：签名不同说明它们是四种不同粒度的后处理，不是同一件事的重复；顺序是硬依赖，不是惯例。
第二章

变换：四类操作

管道第 ② 段。「变换」不是钦点的固定几种操作——把 145 个实现里统计到的变换函数按改动的对象归类，恰好是四类：改数值、改逻辑位置、改 bit 编码、改字节解释。每类解决一个不同层面的「checkpoint 和 kernel 不一致」。

2.1 数值重量化：合并分片 Scale

vLLM 把 Q/K/V 三个投影融合成一个 QKVParallelLinear，但 checkpoint 中每个分片有独立的 scale。scaled_mm 只接受整个权重用一个 scale——所以必须取三者最大值（统计里 .max() 的来源），再对每个分片反量化、用统一 scale 重新量化（scaled_fp8_quant() 的来源）：

三个独立 scale 的分片必须统一为一个 scale，否则 matmul 计算的数值全部错误
# w8a8_utils.py — process_fp8_weight_tensor_strategy() 核心逻辑 max_w_scale = weight_scale.max() for 每个逻辑分片 (q / k / v): weight_dq = per_tensor_dequantize(shard, weight_scale[idx]) shard, _ = ops.scaled_fp8_quant(weight_dq, max_w_scale) # requant

2.2 布局变换：转置 + contiguous

Checkpoint 权重存储为 [N, K]——N 行 K 列，每行是一个输出神经元的权重。但 CUTLASS 的 scaled_mm 要求 [K, N] 布局。转置改变的是矩阵元素的逻辑位置——数值本身不变：

转置：行列互换。A[i][j] 变成 A'[j][i]，数值不变，位置变了

一个容易忽略的细节：.t() 在 PyTorch 里不移动任何数据——它只改 stride 元数据、返回一个视图，物理内存一个字节没动。而底层 kernel（CUTLASS / cuBLAS）为了向量化加载要求输入物理连续：直接喂 non-contiguous 视图，要么报错，要么按连续假设读出错误数据。所以真正的高频组合是 .t().contiguous()——先换逻辑坐标，再显式触发一次物理搬运。这解释了统计里 contiguous（34 个实现、74 次）比 t（30 个、52 次）还高频：一切布局变换最终都要落到密集内存上，view()、permute() 之后同样要跟它。

顺带记住：「变换」这一段的输出几乎必然是新分配的内存，而它的中间产物常常是旧存储的视图——这个「视图 ≠ 数据」的组合到第三章会变成 prefer_copy 的 aliasing 陷阱。

2.3 bit 级重编码：重打包

INT4 量化（GPTQ/AWQ）独有的问题。PyTorch 没有 int4 类型，所以把 8 个 4-bit 值打包进一个 int32。问题是：不同工具的打包方式不一样。统计里的 ops.gptq_marlin_repack、pack_quantized_values_into_int32、NvFP4 的 swizzle_blockscale 都属于这一类。

同样 8 个 INT4 值（a b c d e f g h），AWQ 和 GPTQ/Marlin 的 bit 排列完全不同

重打包改变的是每个 int32 内部各 bit 代表哪个值。矩阵的逻辑形状没变，但字节级的编码方式变了。此外：

  • AWQ 还有维度问题：AWQ 沿输出维度（dim=1）打包，Marlin 要求沿输入维度（dim=0）打包——除了 bit 顺序，还要改打包方向
  • Marlin tile 重排：Marlin kernel 还要把线性存储的权重拆成固定大小的 tile，按 GPU warp 的内存访问模式重排——让 32 个线程能同时高效读取权重

2.4 dtype 迁移

.to() 出现在 22 个实现里：把加载时以高精度存放的 scale 降到 kernel 要求的 dtype、把辅助张量挪到目标设备。没有花哨的数学，但漏掉一步，kernel 读到的就是被错误解释的字节。

四类变换的本质区别：
数值重量化 = 改数值本身（dequant → requant）
布局变换 = 改元素的逻辑位置（数值不变）
bit 级重编码 = 改 bit 在 int32 内的排列（逻辑形状不变）
dtype 迁移 = 改字节的解释方式

2.5 三条完整路径实例

FP8——最简路径（变换① + ②，然后装回、委派）：

# fp8.py:385 — Fp8LinearMethod.process_weights_after_loading() # 变换①: 合并分片 scale（QKV 融合层需要） weight, weight_scale, input_scale = process_fp8_weight_tensor_strategy( weight, weight_scale, layer.logical_widths, # logical_widths = [q, k, v] getattr(layer, "input_scale", None), ) # 变换②: 转置 weight = weight.t() # [N, K] → [K, N]，CUTLASS 要求列主序 # 装回: 替换参数（→ 第三章） replace_parameter(layer, "weight", weight.data) replace_parameter(layer, "weight_scale", weight_scale.data) # 委派: 让选中的 kernel 做后端专属的定稿（→ 第三章） self.fp8_linear.process_weights_after_loading(layer)

GPTQ——委派链最深的路径（QuantMethod 层几乎全部转交 kernel 层）：

# auto_gptq.py:453 → 整体委派给 kernels/linear/mixed_precision/marlin.py:88 # 变换②': g_idx 排序（act_order=True 时，Marlin 靠排序索引保内存局部性） g_idx, sort_indices = marlin_sort_g_idx(layer.g_idx) # 变换③: repack 成 Marlin tile 格式（warp-level shuffle 读权重，不 repack 读错位置） weight = ops.gptq_marlin_repack(qweight, perm=sort_indices, size_k=padded_k, size_n=padded_n, num_bits=4) # Scale 填充 + 排列，随后 replace_parameter 装回 scales = marlin_permute_scales(marlin_pad_scales(scales, ...))

AWQ 不是第三条路：_convert_awq_to_standard_format()（awq_marlin.py:493）先把交错的 bit 排列和打包维度归一化成标准 GPTQ 格式（2.3 的图展示过差异），然后走和 GPTQ 完全相同的 Marlin 委派链。

2.6 什么情况下才需要副本

前面五节讲的变换全都是替换：转置完、repack 完，旧格式就没人要了，replace_parameter 装回去就结束。副本是另一回事——它意味着旧格式还有人在用。

在 vLLM 里这基本只有一种成因：prefill 和 decode 要不同的权重布局，而且两条路径同时都得活着。canonical 参数喂 prefill 的 chunked kernel，fused decode kernel 要另一种连续布局——不能二选一，只能多存一份。

但「多存一份」优先应该是视图而不是副本。只要两种布局能用同一块存储的不同 shape/stride 表达，视图就严格更优：不花显存，而且母体被 copy_() 改写时它自动跟着新。vLLM 里最干净的例子是 mamba2——conv_weights 是 self.conv1d.weight.view(...)，注册成 persistent=False 的 buffer，而且建在 __init__ 里（mamba_mixer2.py:441）。它不需要被维护，因为它不是一份数据，是同一份数据的另一种看法。

只有视图顶不住——真需要一次物理重排——才轮到副本。K3 的 conv 就是：主参数按 [3·H·128, 4] 存，fused decode kernel 要 [3, 4, H·128] 且必须连续，stride 表达不出来。

于是问题只剩「什么时候生成它」，这也是本分支的核心改动：保留 fused decode 需要的副本，但不在 checkpoint loader 里更新它，而是在所有 canonical 权重加载完成之后统一生成。

这就是 process_weights_after_loading 这个名字的正面表述——after loading 是契约，不是描述。weight loader 每次被调用只看得见自己那一片分片，谁都不知道自己是不是最后一个；在 loader 里维护派生副本，等于赌加载顺序。

反面教材见「显存生命周期」篇第六章的 P5「loader 副作用重建」和 R3b「搭便车重建」：两者都是拿一个局部信号去近似「所有权重都到齐了」这个全局事实。pwal 是唯一持有那个事实的位置。K3 conv 上具体怎么翻车的，见事故记录篇 7c52395d。
第三章

装回与委派：replace_parameter 家族与 kernel 两阶段

管道第 ③④⑤ 段。变换完的张量要装回 layer——「装回」看似一行赋值，实际是一个有 6 种写法、约 370 个调用点的家族，写法之间的区别对应三条不同的正确性保证。本章从家族全貌讲到收敛点 replace_parameter，再讲清一个精妙的设计决策（prefer_copy 为什么默认 False），最后是委派机制和 MoE 定稿。

3.2 三条保证的坐标系

为什么装个参数要这么讲究？因为不同写法给出的保证不同。直接 layer.weight = new_tensor 会踩三个坑：

坑 1: torch.compile 失效
直接赋值的张量不是 nn.Parameter，TorchDynamo 看不到它，导致图编译断裂或行为错误。
坑 2: weight_loader 丢失
weight_loader 记录了 TP 分片方式。丢了它，RL 训练循环重新加载权重时会崩溃。
坑 3: CUDA Graph 失效
CUDA Graph 捕获时记录了张量的内存地址。新建张量 = 新地址 = 图重放时访问野指针。

三个坑对应三条保证——注册可见性（在 _parameters 里，torch.compile / state_dict 看得见）、元数据存活（weight_loader 等属性跟着走）、地址稳定（data_ptr 不变，CUDA Graph 重放安全）。把家族主要成员放进这个坐标系：

写法注册可见weight_loader 存活data_ptr 稳定
layer.w = Parameter(new)✓✗ 新对象，属性丢失✗
param.data = new✓ 对象没换✓ 属性挂在对象上，自动存活✗ 底层张量换了
param.copy_(new)✓✓✓ 但要求 shape/dtype 完全一致
replace_parameter(...)✓✓ 显式迁移✓（prefer_copy=True 时）

3.3 replace_parameter：家族的收敛点

# vllm/model_executor/utils.py:47 def replace_parameter(layer, param_name, new_data, prefer_copy=False): # 语义 1: new_data=None → 删除（覆盖删除组写法） if new_data is None: setattr(layer, param_name, None); return # 语义 2: prefer_copy=True 且 shape/dtype/device 匹配 → 原地拷贝 # 保留内存地址（覆盖 copy_ 写法，CUDA Graph 安全） if prefer_copy and 兼容: old_param.copy_(new_data); return # 语义 3: 默认 → 新建 Parameter + 迁移 weight_loader # （覆盖「直接赋值 + 手工搬元数据」写法；旧参数不存在则是新增） new_param = nn.Parameter(new_data, requires_grad=False) if hasattr(old_param, "weight_loader"): set_weight_attrs(new_param, {"weight_loader": old_param.weight_loader}) setattr(layer, param_name, new_param)

它把家族里散落的手工写法收进一个入口：删除、原地更新、重绑定、新增（getattr(layer, name, None) 允许旧参数不存在）——4 种终态需求全覆盖。剩下的写法要么是历史遗留（122 处直接赋值在逐步迁移），要么有正当理由：param.data = new 常出现在变换闭包里，因为它天然保留 BasevLLMParameter 对象及其布局属性（permute_param_layout_ 要读它们），闭包只负责换数据；register_parameter 用于新增 checkpoint 里不存在的参数（如 Marlin 的 input_global_scale）。

3.4 为什么 prefer_copy 默认 False？首载与重载的本质区别

一个自然的疑问：既然原地拷贝保住所有三条保证，为什么不默认开？答案藏在时间轴里——地址稳定只在「已有人引用旧地址」时才有意义：

左：首次加载时 pwal 发生在 CUDA Graph 捕获之前——没人引用旧地址，重绑定随便换。右：RL 重载时 pwal 重跑，此时图已持有地址——必须原地拷贝

全代码库 prefer_copy=True 只有一处调用，且写法印证了这个时间轴（unquantized_fused_moe_method.py:176）：

# 首次调用: moe_kernel 尚未建立 → 正常重绑定 # RL 权重更新重跑 pwal: kernel 已建立、CUDA Graph 可能已捕获地址 → 原地拷贝 is_weight_update = self.moe_kernel is not None replace_parameter(layer, "w13_weight", w13_new, prefer_copy=is_weight_update) replace_parameter(layer, "w2_weight", w2_new, prefer_copy=is_weight_update)

除了「首载保地址零收益」，默认 True 还有一个更致命的问题——aliasing。变换输出经常是旧参数存储的视图（2.2 节讲过 .t() 不搬数据）。对重叠内存做 old.copy_(view_of_old) 在 PyTorch 是未定义行为，而方阵恰好能通过 shape/dtype 检查：

方阵转置视图与原参数共享同一块 storage。逐元素 copy_ 时先写 b 的位置（← d），随后要读 b 时读到的已是脏值——静默数据损坏，无任何报错

归纳成三个理由：

  • Aliasing 静默损坏：opt-in 把「new_data 不 alias 旧存储」的举证责任交给唯一知道数据来历的调用者
  • 首载保地址零收益，反有语义成本：copy 路径会保留旧参数上已过期的 checkpoint 布局属性（output_dim/packed_dim）；rebind 故意换成干净对象、只迁移 weight_loader
  • 多数路径 copy 根本不可能：变换后 shape/dtype 大概率已变（转置、int32 打包、BF16→FP8），默认 True 只是白做一遍兼容检查
更准确的表述：这不该是布尔默认值，而是「首载 rebind、重载 copy」的自动判断。现状把判断留给调用者（is_weight_update）；要彻底统一，可以让 replace_parameter 自己感知 reload 状态 + 做 storage 重叠检测，届时 prefer_copy 参数本身都可以消失。

3.6 委派：kernel 两阶段生命周期

统计表第三名是 pwal 自己（41 个实现委派内层对象的同名方法）——因为后处理是两级的：QuantMethod 层管方案语义（scale 合并、AWQ→GPTQ 格式归一），Kernel 层管后端布局（Marlin repack、CUTLASS pad、swizzle）。两级用同名方法串成两阶段生命周期：

阶段 1：create_weights() 中选择 + 创建 kernel
choose_scaled_mm_linear_kernel() 按优先级遍历候选 kernel 列表
→ 每个候选调用 is_supported(gpu) + can_implement(config)
→ 第一个通过的被实例化为 self.fp8_linear 或 self.kernel
阶段 2：process_weights_after_loading() 中定稿
self.kernel.process_weights_after_loading(layer)
→ 权重已加载完毕，现在可以做依赖实际数据的操作
→ Marlin：repack 权重 + permute scale + 分配 workspace
→ CUTLASS FP8：通常是 no-op（转置已在 QuantMethod 层完成）
为什么分两阶段？因为 create_weights() 时权重还没加载——只有 shape 和 dtype 信息，没有实际数据。而 Marlin 的 repack、DeepGEMM 的 pad 等操作需要读取实际权重值才能执行。所以把数据无关的操作（选 kernel、定义参数 shape）放在阶段 1，把数据相关的操作（repack、permute）放在阶段 2。

Kernel 层内部有两个标准工具，都是「变换 + 装回」的封装：

# kernels/linear/mixed_precision/MPLinearKernel.py:71 def _transform_param(self, layer, name, fn): new_param = fn(getattr(layer, name)) # 变换 replace_parameter(layer, name, # 装回 torch.nn.Parameter(new_param.data, requires_grad=False)) # parameter.py:544 — 变换前先把权重「摆正」 permute_param_layout_(param, input_dim=0, output_dim=1, packed_dim=0) # 各家 checkpoint 的打包维度不一致（AWQ 按 dim=1、GPTQ 按 dim=0） # 先规范到统一朝向，后续 repack 逻辑就只需要写一份

第四章

从打补丁到立契约：weight update 需要怎样的后处理

RL weight update 对权重管道只有两个诉求：尽可能 eager——weight_loader 里的 copy_ 写入就是终态，最好不需要任何收尾动作；地址永不变——CUDA graph 捕获了每个张量的 data_ptr，任何重分配都是静默损坏。但现实是"重载后重跑 pwal"这条路每隔几周就出一个新 bug、打一个新补丁。这一章解释为什么补丁永远打不完，以及用什么代替它。

4.1 病根：契约真空

先看 pwal 的全部显式契约——base class 上的原文，三行 docstring：

# quantization/base_config.py:67 — 这就是 pwal 的全部显式契约 def process_weights_after_loading(self, layer: nn.Module) -> None: """Process the weight after loading. This can be used for example, to transpose weights for computation. """ return

没有前置条件，没有调用次数限制，没有允许副作用的清单。88 个实现在这片真空里各自演化，沉淀出一套谁都没写下来、但人人都在依赖的隐式假设。weight update 把每一条都打破了——而且每一条断裂处，都已经有真实补丁在替它挨打：

隐式假设weight update 打破它病症与实证
只会被调用一次finish 时再调一次double-transpose（Fp8LinearMethod）、double-fold（TRTLLM NVFP4 clamp/beta）、destructive fusion 累乘。树内散落 _already_called flag（online/fp8 ×5、nvfp4、mxfp4、modelopt），layerwise reload 还要先 delattr 清 flag 再调
在 graph capture 之前调update 发生在 capture 之后参数重绑 → graph 读旧地址。#52626：mHC broadcast 每次 rebind 新张量，refit 后 graph 一直读 stale 值。MLA W_UV/W_UK_T、marlin g_idx 各自散补 prefer_copy=True
可自由重建对象
（Parameter / kernel / config）		编译产物已握着旧对象引用#50074：online NVFP4 每次 reload 重建 moe_kernel，5 次 reload 后 11.1% 非有限输出。#49695：TRTLLM kernel 内部派生张量（gemm1_alpha、_g1_alphas…）graph-visible 却被当 rebuild-on-demand scratch——广义修复尝试，已关闭
checkpoint 格式此后不再需要update 推来的恰恰是 checkpoint 格式不可逆 repack（Marlin / AITER shuffle 无逆变换）；per-tensor FP8 转置后 output_dim 标记不更新 → 下次 weight_loader 按旧标记切 TP shard，shape mismatch
结论：88 个实现全部"合法"。它们没有违反任何写下来的契约——因为根本没有写下来的契约。每个作者只能在生产环境撞上一种病症之后修补自己的模块：#50074 的作者撞上非有限输出，#52626 的作者撞上 stale broadcast。契约不立，补丁不止——下一个新 quant method 一定会再犯。

真空之上还有一层语义混淆：pwal 名下装着两种本质不同的操作——格式转换（同一份数据换排列，只在 checkpoint ≠ kernel 格式时需要）和派生状态计算（从权重 X 算出 Y，源一变就要重算）。重跑条件不同的两件事混在一个函数里，"update 后要不要重跑 pwal"这个问题本身就无法回答。

4.2 解法：refresh_derived_state——weight-update-native 的契约

不再一个一个打补丁，把补丁们各自摸索出的规则升格为契约。finish 阶段不再"重跑 pwal"，统一走一个新入口 refresh_derived_state，三条条款，每条正对 4.1 表里的一处断裂：

条款一
In-place
所有写入走 copy_ / resize_+copy_，data_ptr 不变——在 graph capture 之后调用是安全的
条款二
幂等
调用任意次结果一致——_already_called flag 整体退役，destructive 累积不再允许
条款三
增量
无格式差的层直接 return——不为不需要转换的层制造风险
finish_weight_update() for module in model: module.refresh_derived_state() ├─ 无格式差的层（BF16 dense、Triton/CUTLASS MoE） │ return # 条款三：eager copy_ 已是终态 ├─ 有格式差的层（DeepGEMM / FlashInfer / AITER / Marlin …） │ 复用 pwal 的转换代码，以 update 模式执行 # 条款一 │ （prefer_copy 写入，不重建 kernel） └─ 派生状态（W_UK_T/W_UV、norm weights、alphas、mHC broadcast） 从更新后的源权重重算，copy_ 进预分配张量 # 条款一 + 二

已有补丁全部被契约收编：#52626 的 mHC broadcast 归入"派生状态"分支；#50074 与 unquantized_moe 的 kernel 保持归入"格式转换 + kernel 不重建"分支；散落各处的 _already_called flag 被幂等条款整体取代。pwal 归还给冷启动——它在整个进程生命周期里只跑一次，此后永不再调。

4.3 复用而非重写：双模式 pwal 的五条需求

契约不要求重写 88 个实现——格式转换的代码逻辑本身没有错，错的是它的执行方式假设了冷启动。3.4 节看到的 is_weight_update 模式（同一份转换代码、两种执行方式）就是答案的雏形，把它推广成标准需要满足五条：

需求说明对应病症
R1模式信号统一实现内部可靠区分冷启动 vs update。moe_kernel is not None 是惯例不是契约——dense 方法没有 kernel 对象可查_already_called flag 乱象
R2写入 in-placeprefer_copy / resize_+copy_。前提是目标已存在：W_UV/W_UK_T、mHC broadcast 这类派生张量必须在 __init__ 预分配，否则首次 prefer_copy 落空#52626；MLA/marlin 散补
R3一次性对象只建一次kernel、quant_config、routing tables 在 update 分支跳过#50074、#49695
R4输入必须是 checkpoint 格式幂等的前提——不可对已是 kernel 格式的数据二次转换。shape 变化的层需要 restore（resize_ 回 checkpoint shape）再装载不可逆 repack、dim 标记 mismatch
R5无 destructive 累积scale 融合（weight_scale_2 *= input_scale）改为保留原始值、每次重算，不能在已融合值上累乘#49695 的 double-fold

4.4 加在哪里：两个表面，三层覆盖

诚实报数——受影响面比"改几个方法"大得多。结构性扫描（#49695 做过一次，本仓库核对过）显示有两个表面：

表面 A：quant_method 层。self.moe_kernel = 赋值出现在 24 个文件（fp8、modelopt、mxfp4、moe_wna16、auto_gptq/awq、humming、compressed_tensors ×8、quark、online ×5、inc）——每一个都是"update 时重建 kernel"的潜在病灶，外加各自 pwal 里的参数重绑。

表面 B：kernel/experts 对象内部的派生张量。TRTLLM FP8/NVFP4、FlashInfer CUTLASS/B12x、vLLM CUTLASS 等 experts 类在 __init__/pwal 里分配 graph-visible 张量（gemm1_alpha/beta/clamp_limit、_g1_alphas…）。#49695 一语中的："kernel-object tensors are graph-visible state, but the reload path treats them as rebuild-on-demand scratch"。这个表面需要 experts 级的 refresh 接口（#49695 提议的 refresh_after_weight_reload）。

覆盖策略三层，不是全量铺开：

  • 契约 + dispatch（2 个位置）：quant_method 级能力声明 + experts 级 refresh 接口（默认 no-op）。#49695 的关键教训：keep-kernel guard 必须是 capability-gated allowlist，不能盲目 moe_kernel is not None——experts 不实现派生张量 refresh 却保留 kernel，比重建更糟（stale state 且没有重建来兜底）
  • 双模式改造（v1 约 10–12 个 method 类 + 4–6 个 experts 类）：范围由 RL 框架格式审计决定——veRL/OpenRLHF 发 BF16、Miles 发 FP8 预量化 + INT4 推理侧量化、NeMo-RL 有 QARL 流程。落到实现上：unquantized、Fp8 dense/MoE、wNa16/Marlin INT4（Miles 场景，SGLang 已为此打过 resize_+copy_ 补丁）、TRTLLM 系 experts refresh、MLA 预分配；online 系列归 v2
  • 长尾零改动（fail-closed）：不预测"哪些格式永远不会被 update"——未声明能力的组合（GGUF、HQQ、BitNet…）在 start 就被拒绝，而不是默默跑冷启动语义然后静默损坏。契约因此可以增量推进，不需要一夜改完 24+ 个文件

4.5 全量普查：88 个实现落进三个分支

每一层在 finish 时走 dispatch 树的哪个分支，由 quant_method + kernel backend 的组合决定——create_weights() 时已经确定，不需要任何运行时探测。契约不是空架子：把 88 个量化层实现和挂载点 ② ③ ④ 全部按分支归类，每个分支的人口、代表和 finish 动作如下。

分支一 return：约 40 个实现 + 无格式差的 backend 组合

普查里最大的群体是纯委派 / noop——只做 self.kernel.process_weights_after_loading(layer) 或干脆 pass，不碰权重数据。再加上"有转换代码、但对当前 backend 恰好是 no-op"的组合（block FP8 + Triton/VLLM_CUTLASS、BF16 dense）。这些层 weight_loader 的 copy_ 就是终态，finish 零动作——RL 最常见的 BF16 / Triton 路径整条落在这里，这正是"尽可能 eager"的落点。
