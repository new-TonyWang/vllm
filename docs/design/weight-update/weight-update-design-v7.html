1. 第一性原理与不可动摇的约束

核心约束

  1. data_ptr() 全程不变 — CUDA graph 已 capture，不重新 capture。所有写入必须用 copy_ 或 resize_+copy_，不允许 replace_parameter 创建新 tensor
  2. 坚定复用 model.load_weights() — 不绕过 AutoWeightsLoader。530+ 模型的 name routing、TP shard、stacked_params_mapping 全部复用
  3. 不使用 layerwise — 不依赖 meta device restore / materialize / kernel_tensors / online_process_loader
  4. 永远不考虑 hot-swap — 始终 drain → update → resume

设计决策

  • 三个扩展点：
    • 扩展点 A（weight_loader）：load 阶段，per-param。六类分派（①②③ eager 完结 / ④⑤⑥ 暂存等 finish），详见 Per-Param Copy 分类
    • 扩展点 B（refresh_derived_state）：finish 阶段，per-module。新接口，不是 PWAL。契约：in-place、幂等、增量。变换逻辑从 PWAL 提取成纯函数共享。只有 ⑤⑥ 类层实现，其余继承 no-op
    • 扩展点 C（restore_weights_before_loading）：start 阶段，per-module。⑤ 类层把 param 从 runtime 布局恢复回 checkpoint 布局（transpose / resize_ 回原 shape），让 weight_loader 能正常 copy_。每个 quant_method 实现自己的逆操作，默认 no-op。SGLang wNa16 已有此接口
  • Flag 开关新旧调用栈：新的 start(C) → load(A) → finish(B) 调用栈通过一个 flag 启用（如 use_new_weight_update=True）。旧调用栈（直接 load_weights + 无条件重跑 PWAL）仍然保留，作为 fallback——它能兼容大部分 dtype 匹配 + 无布局变换的场景（①②类）。新调用栈只在 flag 开启时走，逐步验证后切为默认
  • Fail-closed：dtype 不匹配且无在线量化 loader → raise error

3. RL 训练框架发送什么

框架发送 dtype预量化？
veRL BF16 否
OpenRLHF BF16 否
Miles BF16 或 FP8 可选：FP8 在训练侧量化后发送

结论：所有主流框架默认发 BF16。Miles 是唯一支持训练侧预量化的。v1 只支持 dtype 匹配（BF16↔BF16, FP8↔FP8），覆盖 95%+ 场景。

4. 调用栈设计

Start 阶段

0 NCCLEngine.start_weight_update()
→ drain requests
C 扩展点 C：restore_weights_before_loading（per-module）
遍历 model.modules()，对 ⑤ 类层调 quant_method.restore_weights_before_loading(layer)。
每个 quant_method 实现自己的逆操作（transpose 回去 / resize_ 回原 shape），默认 no-op。
目的：让 param 恢复成 checkpoint 布局，weight_loader 才能正确工作。
为什么需要 restore——weight_loader 只认 checkpoint 布局：weight_loader 在 create_weights 时被设定好（output_dim=0, input_dim=1），之后永远按 checkpoint 布局的规则计算 TP shard offset 和 copy_ 位置。它不知道 PWAL 后来做了什么变换，也没有任何机制更新自己的标记。例如 FP8 per-tensor dense 的 PWAL 把 [N, K] transpose 成 [K, N]，但 output_dim 还是 0——update 时 trainer 发 [N, K] 的 tensor，weight_loader 按旧标记沿 dim=0 切 shard，往 [K, N] 的 param 里 copy_，shape 不匹配直接报错。restore 把 param 变回 weight_loader 认识的布局，weight_loader 不需要任何改动。

Receive 阶段

1 NCCLEngine.receive_weights(update_info)
→ NCCL broadcast 接收 tensor
2 model.load_weights([(name, weight)])
→ AutoWeightsLoader: checkpoint name → param routing（stacked_params / expert_params）
→ 调 param.weight_loader(param, loaded_weight, ...)
A 扩展点 A：weight_loader（per-param）
冷启动时已绑定在 param 上，weight update 时直接复用。按到达格式 vs param 格式的差异分六类（①②③ eager 完结 / ④⑤⑥ 暂存等 finish）。
详见 Per-Param Copy 分类。

Finish 阶段

B 扩展点 B：refresh_derived_state
做什么：扫一遍模型所有层，每层调 refresh_derived_state()。这是一个新接口，不是 PWAL。

三个分支（冷启动定死，运行时只查表）：
• 大多数层 → return，什么都不做。copy 阶段已经是终态。 NOOP
• 格式转换层（⑤ 类：Marlin / DEEPGEMM / FLASHINFER_TRTLLM / AITER）→ 读出 copy 阶段存进去的 checkpoint 格式数据，调共享的变换纯函数重新排列，resize_+copy_ 写回 runtime 布局。不重建 kernel。 复用 PWAL 变换逻辑
• 派生状态（⑥ 类）→ 从已更新的 param 本体重新计算二级张量，copy_ 进预分配好的位置。 DERIVE
    W_UK_T / W_UV ← kv_b_proj（MLA 投影矩阵）
    _g1_alphas ← w1_scale × a1_scale（MoE 融合系数）
    mHC broadcast / HPC norm（DS4 广播副本）
为什么是新接口而不是重跑 PWAL：PWAL 的契约允许重分配 tensor、重建 kernel、不保证幂等——这些在 update 时全是 bug 来源（PWAL 管道 ch4 有完整证据）。refresh_derived_state 的契约从出生就是 in-place、幂等、增量。变换逻辑从 PWAL 提取成纯函数，两个入口共享计算代码、各自用不同的写回方式（PWAL 用 replace_parameter，refresh 用 copy_）。只有需要 finish 做事的层才实现它，其余层继承默认的 no-op。

5. PWAL 分类与派生状态（摘要）

88 个 PWAL 实现按 finish 分支全量归类：约 40 个纯委派/noop（finish 零动作，eager copy_ 即终态）、约 35 个格式转换（update 模式复用转换代码，prefer_copy / restore + resize_+copy_）、约 5 个 derived-only + 挂载点 ②③④ 全部（refresh 重算）、13 个在线量化（v1 fail-closed，v2 迁入 weight_loader 包装）。逐实现普查表、派生状态完整清单（W_UK_T/W_UV、W_K、W_UK_T_dcp_qrep、_g1_alphas、HPC norm、mHC broadcast）与完整论证见 PWAL 管道 · 第四章 4.5「全量普查」。

影响设计的两个硬结论保留在此：
① 格式转换操作的是整个 fused tensor（w13_weight 含全部 expert），必须等所有权重到齐——不能 eager，这是 finish 阶段存在的根本理由。
② MLA 派生有 3 条路径（BF16 / MXFP4 / FP8），refresh 按 backend 分派，复用 _derive_absorbed_attention；派生链有两级（W_UK_T_dcp_qrep ← W_UK_T），刷新按依赖顺序。

6. 在线量化路径分析

现有机制的局限

vLLM 现有的在线量化（vllm/model_executor/layers/quantization/online/）量化逻辑全在 PWAL 里，不在 weight_loader 里。冷启动流程：

create_weights  → BF16 param（无包装）
load_weights    → weight_loader 原封不动，BF16 copy_ 进 BF16 param
PWAL            → BF16 → FP8/NVFP4/INT8（replace_parameter）

PWAL 之后 param 变成 FP8。Weight update 时 trainer 发 BF16 → copy_ 进 FP8 param → dtype mismatch → 失败。

现有 weight_loader 包装

vLLM 已有的 weight_loader 包装都不是在线量化：

包装位置做什么是在线量化？
MoeWNA16Method.get_weight_loadermoe_wna16.py:520AWQ/GPTQ INT4 bit repackNo，格式转换
Mxfp4MoEMethod.get_scale_weight_loadermxfp4.py:623MXFP4 scale 路由No，scale 路由
make_online_process_loaderlayerwise.py:146buffer → materialize → PWALYes，但是重量级 layerwise

v2 方案：轻量 weight_loader 包装

在 create_weights 时永久包装 weight_loader，加入在线量化逻辑：

def fp8_block_online_loader(param, loaded_weight, **kwargs):
    if loaded_weight.dtype == param.dtype:
        original_loader(param, loaded_weight, **kwargs)  # FP8→FP8
    else:
        fp8_data, scale = per_block_cast_to_fp8(loaded_weight)  # BF16→FP8
        original_loader(param, fp8_data, **kwargs)
        copy_scale(param, scale, **kwargs)
Block FP8 在线量化可以零 buffer 实现：每个 shard 到达就独立量化（block scale 是局部的）。冷启动和 weight update 共用一个 loader。不需要 PWAL，不需要 layerwise，不需要 buffer。

Per-tensor FP8 在线量化需要 buffer：fused param（qkv_proj, w13_weight）的 per-tensor scale 需要全部 shard 到齐才能算 absmax。Per-tensor FP8 已经很少使用（主流是 block FP8），可 defer 或用 SGLang 的 w1+w3 闭包 buffer 模式。

7. Edge Cases：主流模型逐个分析

DeepSeek-V3 / R1（MLA + FP8 MoE）

组件Weight Update 行为需要什么
Attention kv_b_projcopy_ 进 kv_b_proj paramfinish 时 refresh W_UK_T / W_UV
Attention q/o projcopy_无
MoE w13/w2（block FP8）copy_（checkpoint layout = runtime layout for block FP8）无
MoE w13/w2（per-tensor FP8）copy_ + finish 时 kernel shuffle via PWALrestore → copy_ → PWAL (w1+w3 scale requantize + kernel shuffle)
_g1_alphas（per-tensor 路径）—finish 时 refresh
Block FP8 vs Per-tensor FP8 的关键区别：Block FP8 的 PWAL 不 transpose weight（fp8.py:400 附近），不调 process_fp8_weight_tensor_strategy。所以 block FP8 MoE 的 checkpoint layout = runtime layout，直接 copy_ 就行。Per-tensor FP8 需要 transpose + scale requantize + kernel shuffle，必须走 PWAL。

DeepSeek-V4-Pro（MLA + FP4 MoE，per-expert 独立存储）

  • Expert 独立存储（experts.{i}.w1/w2/w3），不 fuse w13
  • 每个 expert 是独立 tensor，在线量化可以 eager 逐 tensor 做
  • 不存在 w1+w3 配对问题
  • MLA 派生同 V3

Kimi K3（MLA + Latent MoE）

  • MLA 派生同 V3（共享 _derive_absorbed_attention）
  • Latent MoE 可能有额外的 prefill/decode 派生权重
  • 如果用 sleep mode（MNNVL fabric），weight update 后需要重新同步 KV state

Llama / Qwen（Dense FFN, BF16）

  • 最简单的 case：所有权重 copy_，无 PWAL，无派生
  • fused gate_up_proj 和 qkv_proj 通过 stacked_params_mapping 自动路由

Mixtral / Qwen3-MoE（FP8 MoE，fused w13）

  • fused w13_weight 格式
  • Block FP8：直接 copy_
  • Per-tensor FP8：需要 PWAL（同 V3）
  • INT4/Marlin：需要 restore → copy_ → PWAL repack（shape 变化）

Mamba / Jamba（State-space models）

  • Mamba 有自定义 weight_loader（mamba_mixer2.py:434）
  • conv1d 权重有特殊 sharding
  • RL 场景中 Mamba 模型极少见，可暂不考虑

8. 场景覆盖与 v1/v2 Scope

v1：trainer 发送的 dtype 与 param 匹配

覆盖 95%+ 的 RL 场景（veRL/OpenRLHF 发 BF16,Miles 发预量化 FP8）。按 Per-Param 六类分类，v1 处理 ①②⑤⑥：

场景Per-Param 类型C (restore)A (weight_loader)B (refresh)
BF16 dense/MoE ① — copy_ return
Block FP8 + Triton/CUTLASS ① — copy_ return
Block FP8 + DEEPGEMM/FLASHINFER/AITER ⑤ restore 布局 copy_ 重排回 runtime 布局
Per-tensor FP8 dense ⑤ transpose 回 [N,K] copy_ transpose 回 [K,N]
INT4/Marlin repack ⑤ resize_ 回原 shape copy_ Marlin repack
MLA（DeepSeek V2/V3/R1, K3） ⑥ — copy_ kv_b_proj 重算 W_UK_T / W_UV
dtype 不匹配 + 无在线量化 flag — raise ValueError FAIL-CLOSED

v2：trainer 发送 BF16,engine 侧在线量化

在 create_weights 时包装 weight_loader,加入量化逻辑。处理 ③④ 类。

场景Per-Param 类型A (weight_loader)B (refresh)
Block FP8 在线量化 ③ 包装 loader：per-block 量化 + copy_ return
NVFP4 在线量化 ③ (w2) / ④ (w1+w3) 包装 loader：w2 直接量化；w1+w3 per-expert eager 缓冲 return
Per-tensor FP8 在线量化 ④ 包装 loader：per-expert eager 缓冲 return
MXFP4 / MXFP8 / INT8 ③ 包装 loader：per-block/channel 量化 + copy_ return
v2 对 v1 零侵入：包装 loader 在 create_weights 时绑定到 param 上,model.load_weights 调 param.weight_loader 时自动走包装逻辑。v1 的三个扩展点（C/A/B）完全不需要修改。

10. 实施顺序

Phase 0: 前置改动（CUDA graph 安全）

  1. Shape-changing PWAL 的 replace_parameter → resize_+copy_
    • 加 _original_shapes 记录（create_weights 时）
    • 加 is_converted guard（PWAL 幂等性）
    • 加 restore_weights_before_loading（resize_ 回 checkpoint shape）
    • 参考 SGLang compressed_tensors_wNa16_moe.py
  2. MLA _derive_absorbed_attention 中的 replace_parameter 已有 prefer_copy=True，验证 data_ptr 是否真的不变

Phase 1: 核心重构

  1. NCCLEngine.start_weight_update：改为选择性 restore（非 layerwise init）
  2. NCCLEngine.finish_weight_update：改为统一调 refresh_derived_state（内部三分支 dispatch：noop / PWAL 代码复用 update 模式 / 派生重算）
  3. 新增 refresh_derived_state 实现（MLAAttention 3 条路径、TrtLlmFp8MoE）
  4. MTP completeness check 从 load_weights 内部移出
  5. 删除 layerwise 在 WTE 路径中的调用

Phase 2: 在线量化（v2）

  1. Block FP8 在线量化 weight_loader 包装（Fp8BlockOnlineMethod 或等效）
  2. Per-tensor FP8 fused param buffer 逻辑
  3. NVFP4 weight_loader 包装（参考 SGLang nvfp4_online_weight_loader）

Phase 3: 验证

  1. BF16 dense（Llama）：cold start → weight update → verify output
  2. BF16 MoE（Mixtral）：cold start → weight update → verify output
  3. Block FP8 MoE（DeepSeek-V3）：cold start → weight update → verify output
  4. MLA 模型：verify W_UK_T / W_UV refresh correctness
  5. CUDA graph safety：verify data_ptr unchanged after full update cycle

Follow-up：manifest_check（校验所有权重是否到齐）作为后续工作单独实现，不在本轮 scope 内。
