Per-Param Copy 分类

RL 训练发来新权重时，每个 param 怎么接收、什么时候算完

核心问题

训练端发来的权重是原始格式（checkpoint 格式）。显卡里的 param 可能是另一种格式（runtime 格式）——dtype 不同、shape 不同、甚至被压缩过。问题就是：到达的 tensor 怎么放进显卡里的 param？

按"到达格式 vs param 格式"的差异程度，所有 param 分成六类。前三类 copy 完就是终态，后三类 copy 只是暂存，需要 finish 阶段统一处理。

Copy 完即终态

EAGER 完结 · finish 时 return
① 格式完全一样
到达 BF16，param 也是 BF16，shape 一样。
BF16 tensor → copy_ → done
大多数层都是这个——attention 的 qkv、dense mlp、layernorm。占 88 个 PWAL 实现中的绝大部分。
Miles/SGLang 完全相同——weight_loader 的 copy_，主线和 Miles 无区别。
② dtype 不同，纯换单位
到达 BF16，param 存的是 FP16（或反过来）。copy_ 自动转换 dtype，一对一，不需要额外信息。
BF16 tensor → copy_（自动 cast） → FP16 param · done
就像把美元换成欧元——汇率固定、一步完成。
Miles/SGLang 完全相同——copy_ 自动 cast。
③ dtype 不同，需要量化，但 scale 自包含
到达 BF16，param 存的是 FP8 + 一个 scale。不能裸 copy_——要先算 scale 再压缩。但关键是：算 scale 只需要看这一片 tensor 本身（blockwise / per-channel），不需要等其他 tensor 到齐。所以可以到一片、量化一片、存一片。
BF16 tensor 一片 → 量化（算 scale + 压缩） → FP8 qweight + scale · done
② 和 ③ 的区别：② 是换单位（BF16→FP16，copy_ 自动做，一个输入一个输出）；③ 是压缩（BF16→FP8，要算缩放比例，一个输入产生两个输出：压缩后的权重 + scale）。但两者都是"到一片处理一片"，不需要等别人。
③ vs ④ 的分界线——"scale 的范围是否落在单次到达的一片里"：
• ③ 自包含：blockwise（128×128 块内）、per-channel（一行）、per-tensor 但 tensor 没 fuse 别人（如 NVFP4 的 w2，一个 expert 独立到达）
• ④ 非自包含：per-tensor 但 tensor 是 fused 的（如 w1+w3 分两次到，per-tensor scale 要看 cat 后的整体）→ 见下方 ④
Miles/SGLang Miles trainer 侧预量化：quantize_params 管道在发送前量化成 checkpoint 格式 → engine 收到 dtype 已匹配，变成 ①。SGLang engine 侧没有 ③ 的 loader 包装（NVFP4 的 w2 直接量化是 ③，但 w1+w3 缓冲属于 ④——见下方）。其他量化类型（FP8 block / per-tensor / dense）无 loader 包装，dtype 不匹配时 copy_ 做裸 cast（scale=1），超出 FP8 范围的值变 nan，小值归零——静默损坏，不报错。

Copy 只是暂存，需要 finish

需要 FINISH · 统一 refresh 时处理
④ 需要量化，但 scale 要看全局
到达 BF16，param 存的是 FP8 + per-tensor scale。per-tensor = 整个 fused param（比如 gate+up 合并后）只有一个 scale。算这个 scale 需要看所有 tensor 的最大值——但 tensor 是分批到达的，没全到就不知道全局最大值是多少。
BF16 tensor 一片 → copy_ 进 staging buffer（暂存原始值） → 等全部到齐
finish 时 → 看完整 staging → 算全局 scale → 量化 → FP8 qweight + scale · done
③ 和 ④ 的区别：③ 的 scale 只看这一片（blockwise / per-channel），到一片算一片；④ 的 scale 要看所有片拼起来的全局（per-tensor），必须等齐。
能不能像 SGLang 那样 eager+缓冲？可以，但取决于 fused param 多大：
• 小融合（qkv_proj / gate_up_proj，2-3 片）：每片到达时记录局部 absmax，最后一片到齐时已知全局 scale → 立刻量化全部暂存片。BF16 暂存 ≈ 几十 MB，可接受。SGLang 的 cached_a_proj 就是这个模式。
• 大融合（MoE w13_weight，256 experts × gate+up）：BF16 暂存 ≈ 17 GB（DeepSeek-V3, TP=8）。不可接受，必须放 finish 或彻底规避。
④ 的三条出路（我们选路 3）：
路 1: staging buffer——单独分配 BF16 buffer 暂存到达的权重，finish 时统一量化写入 FP8 param。代价：buffer = 整个 fused w13 的 BF16 大小（DeepSeek-V3 TP=8 约 17GB）。太贵。
路 2: restore 成 BF16——学 ⑤ 的 restore，start 时把 FP8 param 临时变回 BF16 格式，copy_ BF16→BF16 无问题，finish 时统一量化回 FP8。暂存 = param 本身，不需要额外 buffer。代价：update 窗口内 param 占 2× 显存（BF16 比 FP8 大一倍），但推理已暂停。
路 3: per-expert eager 缓冲 ✓——如果 scale 粒度是 per-expert（每个 expert 的 w1+w3 有自己的 scale），只需缓冲 1 个 expert 的 w1（几 MB），w3 到了就 cat → 量化 → 存入。不跨 expert 等待，不需要 finish。SGLang NVFP4 的 pending_w13_weights 就是这个模式。
我们选路 3：per-expert 粒度的 eager 缓冲。主流量化已转向 block FP8（③ 自包含），per-tensor 的 ④ 场景越来越少，仅剩的（NVFP4 w1+w3）在 per-expert 粒度完全可以 eager 解决。详细的到达粒度 vs 量化粒度分析见 Fused Param Scale Buffer。
Miles/SGLang NVFP4 MoE 是 ④ 的 eager 解法：nvfp4_online.py:get_online_weight_loader 在 weight_loader 内做缓冲——w2（不 fuse）直接量化（实为 ③）；w1+w3 用 pending_w13_weights 缓冲，pair 到齐后 cat 一起量化（per-tensor scale 从整体算出），拆回各自 shard 存入。缓冲粒度 = 1 个 expert 的 1 对 w1+w3（很小），不等 finish。
Miles 通过 trainer 侧预量化彻底规避 ④。DeepSeek 的 post_load_weights 里 inverse_transform_scale_ue8m0 逆变换补丁是「不规避就得打补丁」的证据。cached_a_proj / pending_indexer_wk 是 attention 侧的同类 eager 缓冲。
⑤ Shape 不同（repack / 压缩布局）
到达 BF16（shape 100×200），param 被 PWAL 重排成了另一种布局（shape 50×400，或 bit-packed 后更小）。按原始 shape 的地图往重排后的 param 搬——位置全乱。
start 时 → restore: resize_ 回原始 shape
BF16 tensor → copy_ 进已恢复的原始 shape → checkpoint 格式暂存
finish 时 → 重新排列 → resize_ 回 runtime shape → runtime 布局 · done
主要是 INT4/marlin 层。这类层需要三步：恢复形状 → 搬运 → 重新排列。数量很少。
Miles/SGLang Miles 的条件 restore RPC：post_process_weights(restore_weights_before_load=True)，仅当 quant_method 为 compressed-tensors 时触发。engine 侧调 wNa16 的 restore_weights_before_loading（resize_ 回 _original_shapes）。finish 时全量重跑 PWAL 完成 marlin repack。
⑥ 派生状态
param 本体（如 kv_b_proj.weight）格式没变，copy_ 正常落位。但模型里还有从它算出来的二级张量（如 W_UK_T、W_UV——MLA 注意力的投影矩阵），这些必须用新权重重新算一遍。
BF16 kv_b_proj → copy_ 进 param 本体 → 本体更新了，派生还是旧的
finish 时 → 从新本体重算 → copy_ 进预分配的派生张量 → 派生张量更新 · done
派生张量在冷启动时已经建好了（预分配），finish 只是用新值覆盖。地址不变。
Miles/SGLang DeepSeek 的 post_load_weights(weight_names=...)——挂在 load_weights 尾部，增量重算出现 kv_b_proj 的层。用 bind_or_assign(target, source)（target 存在 → copy_，不存在 → 赋值）做 in-place 写入。

总结：六类的分布

类别什么情况copy 时finish 时Miles/SGLang占比
①格式完全一样copy_return相同绝大多数
②纯 dtype castcopy_（自动）return相同
③量化，scale 自包含（block / per-channel / 非 fused per-tensor）量化 + copy_returnMiles 预量化 → 变 ①；NVFP4 w2 直接量化；其他无包装 → 静默损坏
④量化，scale 跨 fused 多片（per-tensor on fused）per-expert eager 缓冲 → 量化 + copy_return（已 eager 完成）NVFP4 pending_w13 eager；Miles 预量化规避极少数
⑤shape 不同（repack）restore 后 copy_重新排列条件 restore + 全量 PWAL
⑥派生状态copy_ 进本体重算派生post_load_weights + bind_or_assign
设计的核心优势：①②③ 占绝大多数，eager copy 零开销完成，finish 直接 return；只有极少数 ④⑤⑥ 需要 finish 做事。而且每个 param 属于哪一类，冷启动时就定死了，运行时只查表——不需要猜、不需要 flag、不需要"这是不是第二次调用"之类的判断。

完整生命周期

start_weight_update()
    ⑤ 类层 restore（resize_ 回 checkpoint shape）

load × N 次（分 bucket 到达）
    每个 param 按类别：
      ①② → copy_
      ③  → 量化 + copy_
      ④  → per-expert eager 缓冲：w1 到了暂存，w3 到了 cat → 量化 → copy_
      ⑤  → copy_（已恢复成 checkpoint shape）
      ⑥  → copy_ 进 param 本体

finish_weight_update()
    每层 refresh_derived_state()：
      ①②③④ → return（④ 已在 load 阶段 eager 完成）
      ⑤    → 重新排列 → resize_ 回 runtime shape
      ⑥    → 从本体重算 → copy_ 进派生张量
为什么没有 graph.refit()：vLLM 不用 CUDA graph refit（PyTorch 也没暴露这个接口）。方案更简单——所有写入用 copy_，地址（data_ptr）不变，已录制的 CUDA graph 自动读到新数据，零额外操作。⑤ 类层的 resize_ 可能换地址，但它发生在推理暂停窗口内、graph 不在 replay，finish 后地址已稳定回 runtime shape。详见 CUDA Graph Refit 机制分析。
