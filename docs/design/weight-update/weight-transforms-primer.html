权重变换入门

PWAL 对权重做的所有操作，从简单到复杂，每个都用大白话讲清楚

第一层：不动数据的操作

reshape / view 零开销 完全可逆
换个看法，数据一个字节没动。就像同一堆积木，你说它是"4 排 × 6 列"还是"2 排 × 12 列"——积木没挪位置，只是你描述它的方式变了。
原始: tensor shape [4096, 11008]   (45M 个数字)
view: tensor shape [4096, 86, 128] (还是 45M 个数字，排列完全一样)

# PyTorch
t2 = t1.view(4096, 86, 128)  # 零拷贝，瞬间完成
t1 = t2.view(4096, 11008)    # 逆操作同样零拷贝
weight update 影响：无。reshape 不改数据，不改地址，copy_ 直接能用。
dtype cast 自动 可逆（有精度损失）
改变每个数字的存储精度。BF16 用 2 字节存一个数，FP32 用 4 字节。就像把"3.14159"四舍五入成"3.14"——信息量变了，但格式简单、规则固定。
BF16 tensor: [1.5, 2.5, 3.5]  (每个 2 字节)
     ↓ copy_ 进 FP16 param
FP16 tensor: [1.5, 2.5, 3.5]  (每个 2 字节，PyTorch 自动转换)
weight update 影响：copy_ 自动做 dtype 转换，不需要额外处理。对应 Per-Param 分类 ②。

第二层：移动数据但规则简单

transpose 要搬数据 完全可逆
行列互换。一张表格的行变成列、列变成行。数据必须物理搬动（因为内存是一行行连续存的，转置后连续性变了）。
原始 [3, 4]:          转置后 [4, 3]:
a b c d               a e i
e f g h       →       b f j
i j k l               c g k
                      d h l

# PyTorch
t2 = t1.t().contiguous()  # .t() 只改 stride，.contiguous() 才真正搬数据
t1 = t2.t().contiguous()  # 再转一次就回来了
谁在用：FP8 per-tensor dense linear 的 PWAL 把 [N, K] 转置成 [K, N]，因为 CUTLASS/cuBLAS 要求列主序输入。
weight update 影响：转置后 shape 变了，weight_loader 的 TP shard 标记(output_dim)对不上。需要扩展点 C restore（transpose 回去），copy_ 完再 transpose 回来。对应 Per-Param 分类 ⑤。
resize_ 可能换地址 数据不保证
改变 tensor 占的显存大小。缩小时截断（多出的数据丢了），扩大时新区域是垃圾值。扩大可能导致显存重新分配（地址变了）。
原始: [4096, 11008]  (占 ~90MB)
resize_: [2048, 5504]  (占 ~22MB，后半段数据丢了)
resize_: [4096, 11008]  (扩回来，但丢的数据不会回来，新区域是垃圾)

# 关键：扩大时如果当前 storage 装不下，PyTorch 分配新的 storage → 地址变了
谁在用：INT4/Marlin repack 后 tensor 变小（bit-packing 压缩）。restore 时需要 resize_ 回原大小让 weight_loader 能 copy_ 进来。
weight update 影响：restore 阶段用 resize_ 回 checkpoint shape（地址可能变，但推理已暂停）。refresh 阶段禁止 resize_——只能用 copy_ 保地址不变。

第三层：量化相关

quantize（量化） 一进两出 可逆（有精度损失）
把高精度数字压缩成低精度 + 一个缩放因子(scale)。比如 BF16 → FP8：先算出这批数字的最大值(amax)，除以 FP8 能表示的最大值(448)得到 scale，然后每个数除以 scale 再四舍五入到 FP8。
BF16 输入:  [300.0, 150.0, 50.0]
amax = 300.0
scale = 300.0 / 448.0 = 0.67

FP8 输出:   [448, 224, 75]    ← 压缩后的整数
scale 输出: 0.67              ← 恢复用的缩放因子

还原: 448 × 0.67 ≈ 300.0  ✓ (有精度损失)
关键点：一个输入产生两个输出（压缩后的权重 + scale）。scale 的计算范围决定了是否需要等其他 tensor 到齐——blockwise scale 看 128×128 块内（自包含），per-tensor scale 看整个 tensor（可能跨多片）。
weight update 影响：blockwise 量化对应 Per-Param ③（自包含，eager 做完）。per-tensor on fused param 对应 ④（需要等配对 tensor 到齐）。
数值重量化 (requant) 改数值
先反量化回高精度，再用新的 scale 重新量化。为什么要这么做？因为 QKV 三片各自有自己的 per-tensor scale，合并成 fused qkv_proj 后需要统一的 scale——必须先还原、拼起来、算新 amax、重新压缩。
# FP8 的 process_fp8_weight_tensor_strategy
q_weight (FP8, scale=0.5) ─┐
k_weight (FP8, scale=0.3) ─┼→ dequant → concat → 算新 amax → requant → fused_qkv (FP8, scale=0.6)
v_weight (FP8, scale=0.4) ─┘
weight update 影响：属于 ④ 类——必须等 q/k/v 三片都到齐才能算统一 scale。用 per-expert eager 缓冲解决。
scale 融合 (scale fusion) 破坏性
把 activation scale 乘进 weight scale，推理时省一次乘法。问题：原始 weight scale 被覆盖了。
# 融合前
output = (input / input_scale) @ (weight * weight_scale)  # 两次 scale 运算

# PWAL 里做融合
weight_scale *= input_scale  # 原始 weight_scale 被覆盖！

# 融合后
output = (input / input_scale) @ (weight * fused_scale)   # 一次 scale 运算
能恢复吗？大多数情况能——input_scale 还保存在 layer 上，除回去就行。但 FlashInfer B12x 不行：它把 scale 融合后设为 1.0，原始值彻底丢了。
weight update 影响：refresh 时需要先"反融合"（除以 input_scale），再用新权重重新融合。属于 R5 契约（无 destructive 累积）。

第四层：硬件专用重排列

repack（硬件 tile 重排） 通常不可逆 各后端不同
把数据按特定 GPU kernel 的最快读取顺序重新排列。每个 kernel 对"怎么读最快"有不同要求，所以每个后端的 repack 规则不同、逆操作也不同。
原始（checkpoint 格式，通用顺序）:
  [a, b, c, d, e, f, g, h]

Marlin repack（按 16 行 tile 交错，让 tensor core 高效读取）:
  [a, e, b, f, c, g, d, h]

AITER shuffle（按 16×16 块排列，AMD CK kernel 专用）:
  [a, c, e, g, b, d, f, h]

FLASHINFER_TRTLLM（2D→4D 分块，128 行 tile）:
  shape 从 [N, K] 变成 [K/128, N, 128]
为什么不可逆？逆操作需要知道排列规则，但 Marlin/AITER/DEEPGEMM 的 repack 逻辑在 C++/CUDA 库里，没有暴露逆函数。光知道原始 shape 不够——resize_ 回原 shape 只改大小不改顺序，数据还是乱的。
后端做了什么可逆？
Triton / VLLM_CUTLASS什么都不做不需要
FLASHINFER_CUTLASSw1/w3 上下半对调(flip)再 flip 一次（自逆）
FLASHINFER_TRTLLM2D→4D 分块 + 行重排可逆（算逆排列）
DEEPGEMMscale 的 TMA 对齐重排没有逆函数
AITER (ROCm)16×16 块重排没有逆函数
Marlinbit 级 tile 交错没有逆函数
weight update 影响：不可逆 repack 的层必须 restore（resize_ 回 checkpoint shape，旧数据不管了）→ copy_ 新数据 → finish 时重新 repack。对应 Per-Param ⑤。restore 不需要"逆 repack"——只需要让 weight_loader 能放进新数据，然后正向重新 repack。
bit 级重编码 (bit packing) 改 shape
INT4 量化没有原生 4-bit 数据类型，所以把两个 4-bit 值打包进一个 8-bit byte（或 8 个进一个 int32）。打包后 tensor 的 shape 变小（宽度减半或更多）。不同工具的打包方式不一样（AWQ vs GPTQ 的 bit 顺序不同）。
原始 INT4 值: [3, 7, 1, 5, 2, 6, 0, 4]  (8 个 4-bit 值)
pack 进 int32: [0x37152604]              (1 个 32-bit 值)

shape 变化: [4096, 11008] → [4096, 11008/8] = [4096, 1376]
weight update 影响：打包后 shape 变小。restore 时 resize_ 回原 shape，copy_ 新数据后重新打包。通常和 Marlin repack 一起做，属于 ⑤。

第五层：派生与副本

派生计算 (derive) 从 X 算 Y 可重算
从一个权重矩阵计算出另一个权重矩阵。源权重变了，派生必须重算。最典型的例子是 MLA：从 kv_b_proj 切分+转置出 W_UK_T 和 W_UV。
# MLA 权重吸收
kv_b_proj [N, qk_nope + v_head]
  ↓ split
  ├→ W_UK [N, qk_nope]  → permute(1,2,0) → W_UK_T [num_heads, proj, latent]
  └→ W_UV [N, v_head]   → transpose       → W_UV   [num_heads, latent, v_head]

# 其他派生例子
_g1_alphas = (w1_scale * a1_scale).squeeze()   # MoE 融合系数
mHC broadcast weights                          # DS4 多头广播副本
HPC norm float32 copies                        # 高精度计算用的 float32 拷贝
weight update 影响：源权重 copy_ 更新后，refresh 阶段重算派生、copy_ 进预分配好的张量。对应 Per-Param ⑥。派生链可能有两级（W_UK_T_dcp_qrep ← W_UK_T ← kv_b_proj），按依赖顺序刷新。
副本生成 (physical copy) 额外一份数据
prefill 和 decode 需要不同的权重布局，有些布局差异无法用 view/stride 表达，必须物理拷贝一份。优先用视图（零显存），只有视图表达不了时才用副本。
# K3 的 conv 权重
主参数:           [3·H·128, 4]     ← prefill 用
fused decode 副本: [3, 4, H·128]    ← decode 用，必须连续，stride 表达不出来

# Mamba2 的 conv 权重（好的例子——用视图代替副本）
conv_weights = self.conv1d.weight.view(...)  # 零拷贝视图，母体更新它自动跟
weight update 影响：源权重更新后，副本也要重新生成。属于 ⑥ 的子类——"从 canonical param 派生的物理副本"。如果是视图则自动跟着更新，无需额外处理。

第六层：装回 layer

replace_parameter 可能换地址
变换完的 tensor 要装回 layer。replace_parameter 是标准入口（137 个调用），有两种模式：
# 模式 1：默认——创建新 Parameter，替换旧的
replace_parameter(layer, "weight", new_tensor)
# → 新 tensor，新地址。冷启动用这个

# 模式 2：prefer_copy——copy_ 进旧 Parameter
replace_parameter(layer, "weight", new_tensor, prefer_copy=True)
# → 旧 tensor 的地址不变，只改数据。weight update 用这个
weight update 影响：我们的 refresh_derived_state 总是用 copy_ 写回（等价于 prefer_copy=True），不创建新 tensor。PWAL 冷启动可以用默认模式（新 tensor）。这就是"变换逻辑共享、写回方式不同"。
copy_ 地址不变 自动 cast
把源 tensor 的数据写入目标 tensor 的已有存储。不分配新内存，不换地址。如果 dtype 不同，自动转换。这是 weight update 最核心的操作。
param = torch.zeros(4096, 11008, dtype=torch.bfloat16)  # 地址 0xABC
new_data = torch.randn(4096, 11008, dtype=torch.bfloat16)
param.copy_(new_data)  # 地址还是 0xABC，数据已更新
# CUDA graph 录的是 0xABC → 自动读到新数据，无需任何处理
weight update 影响：这是唯一保证地址不变的写入方式。我们的设计核心：所有写入最终都通过 copy_。

总结：所有操作一览

操作动数据吗改 shape 吗可逆吗对 weight update 的影响
reshape / view不动改描述，不改存储完全可逆无影响
dtype cast改每个值可能改（byte 宽度变）有精度损失copy_ 自动做
transpose物理搬动行列互换完全可逆需要 restore + refresh
resize_可能换 storage改大小数据不保证restore 可用，refresh 禁止
量化压缩可能变有精度损失③ 或 ④，看 scale 粒度
数值重量化dequant→requant不变有精度损失④，等多片到齐
scale 融合覆盖原值不变大多可逆refresh 需反融合
repack完全重排可能变通常不可逆restore + refresh 重做
bit packing打包变小可逆restore resize_ + refresh repack
派生计算从 X 算 Y新 tensor可重算refresh 重算
副本生成物理拷贝可能不同 layout可重生成refresh 重生成
replace_parameter装回 layer——refresh 用 copy_ 替代
copy_原地写入不变—核心操作，保地址不变

restore 需要做什么：按操作类型

restore 的目标是"把 param 恢复成 weight_loader 认识的 checkpoint 布局"。不需要真正"逆操作"——只需要让新数据能 copy_ 进来就行，旧数据反正要被覆盖。
PWAL 做了什么restore 要做什么为什么这样就够了
什么都没做什么都不做（no-op）param 已经是 checkpoint 格式
transposetranspose 回去完全可逆，数据位置恢复正确
repack（不可逆）resize_ 回 checkpoint shape旧数据是乱的没关系——马上被新数据 copy_ 覆盖
bit packing（shape 变小）resize_ 回原 shape同上，shape 对了 weight_loader 就能正常工作
量化（dtype 变了）不需要 restorecopy_ 自动处理 dtype 转换，或走在线量化 loader
scale 融合不需要 restorerefresh 时从原始值重算，不依赖旧值
派生计算不需要 restore源 param 本体没变布局，refresh 时重算派生
