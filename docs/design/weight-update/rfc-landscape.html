SGLang 生态怎么做 Weight Update：Miles 是正式答案

回答"SGLang 做不做 PWAL"必须先分清两层：主线的裸 RL 通道（veRL 等外部框架在用）和 Miles——SGLang 官方唯一指定的 RL 框架。两者行为相反。生态的正式流程是 Miles 的：update 后无条件全量重跑 PWAL，restore 按需前置。（以下全部按 2026-08 源码逐路径核实。）

Miles 流程（生态正式路径）

1 restore（条件性） — 仅当 quant_method 为 compressed-tensors（int4/fp4，PWAL 会破坏 checkpoint shape）时，先发 restore_weights_before_load RPC：resize_ 回 checkpoint shape
2 trainer 侧转换（eager） — convert_to_hf 管道：去 vocab padding → megatron→HF 布局/命名 → quantize_params 在线量化到 checkpoint 格式（fp8 blockwise / mxfp8 / nvfp4 / int4 四个 quantizer，fp8 的直接 import sglang 的 ue8m0 helper 对齐 scale 格式）
3 传输 + copy — 走 update_weights_from_distributed；engine 侧 weight_loader 只做 TP shard + copy_，零变换
4 finish — post_process_weights(post_process_quantization=True) RPC = 重跑 PWAL，无条件、全模型扫（Miles 注释原话："should always be invoked after weight updating"）；p2p/RDMA 路径额外带 post_load_weights=True 显式触发 MLA 派生（常规路径 load_weights 尾部自带）
划线原则一句话：checkpoint 格式是分界面。传输线上跑的、copy_ 进 param 的，永远是 checkpoint 格式；kernel/runtime 格式的生成永远留在 finish（PWAL）。量化可以 eager——甚至提前到 trainer 侧——因为量化的目标是 checkpoint 格式而不是 kernel 格式。破坏 checkpoint 格式的层（int4）在 load 前先 restore。

主线的四条 update 路径（对照）

路径用途重跑 PWAL？派生状态？

主线里已有我们契约三条的"民间版本"

DeepSeek 系的派生状态刷新（post_load_weights，挂在 load_weights 尾部）已经自发长出了三个机制，与 refresh_derived_state 的三条契约一一对应——但都是局部惯例，没有契约地位：

  • In-place：bind_or_assign(target, source)——target 存在就 copy_（保 data_ptr），不存在才赋值。就是我们的 prefer_copy
  • 增量：RL update 时传入本次到达的 weight_names，只重算出现了 kv_b_proj 的层
  • 幂等（反面教材）：首次 derive 就地把 scale 转成 ue8m0 格式（破坏输入），二次跑必须先 inverse_transform_scale_ue8m0 逆变换——代码注释明说是为 RL 多次加载打的补丁。没有"输入必须是 checkpoint 格式"的契约，就只能在 derive 里塞逆变换
  • 另：wNa16 的 restore_weights_before_loading 已上岸主线，但主线零调用点——RFC 1 上游化停滞的实物证据：零件进了，编排器没进
对我们的启示：Miles 的划线与我们完全一致——eager 只搬 checkpoint 格式，格式转换与派生刷新全在 finish。差别只在 finish 怎么跑：Miles 无条件全量重跑，它跑得起（Triton/marlin 的 PWAL 幂等可重入，restore 兜住 int4）；vLLM 抄不起——DEEPGEMM/FLASHINFER/TRTLLM 后端的 PWAL 有真实开销且重建 kernel 对象，无条件重跑正是 #50074/#49695 的病源。refresh_derived_state = Miles 的分界线 + 契约化的选择性增量（no-op 层 return、in-place 保 data_ptr、kernel 只建一次）。小彩蛋：trainer 侧 _cached_tensors（q_a/kv_a 凑对才发）与 engine 侧 cached_a_proj 是同一个"到达缓冲"手法的两端——小融合可以 eager+缓冲，MoE w13 级的大融合老实放 finish。

SGLang 已踩的坑

这些 bug 和我们要解决的问题完全相同，是 weight update 领域的"共同考试题"。

sgl#26032 PWAL 改 shape 后 weight update crash
场景：NPU 上跑 MoE 模型。冷启动时 PWAL 把 weight transpose 了（改了 shape）。RL weight update 时 trainer 发原始 shape 的 tensor，load_weights 按原始 shape 计算 shard offset → offset 越界 → crash。

根因：PWAL 永久改了 runtime param 的 shape，但 weight_loader 不知道。没人 restore 回 checkpoint shape。

教训：有 layout 转换的层，必须 restore → load → PWAL。不能 "直接 copy_ 进 runtime shape 的 param"。
sgl#27718 MTP draft weights 永远不更新
场景：DeepSeek-V3 用 MTP（multi-token prediction）做 speculative decoding。weight update 只更新 main model，draft model 的 NCCL group 从未建立。

教训：manifest_check 能发现这类遗漏——draft weights 会出现在 "expected but missing" 集合中。
sgl#33698 并发 weight update 互相覆盖
两个并发的 paused weight update 共享 completion state，互相覆盖 future。需要 session/transaction 隔离。

重点 · RFC 1：restore/PWAL 从 Miles fork 上游化——已停滞

sgl#28565 CLOSED — inactivity 自动关闭 对我们最重要

上一节的 Miles 流程里，engine 侧的 restore + 全量 PWAL（post_process_weights 的服务端）只存在于私有 fork sglang-miles，生产跑了很久（INT4 QAT for RL）。上游化 = 把 fork 的改动拆成小 PR 合进官方 main。#28565 就是这个提案——但它依赖 fork 上的其他基础设施（PostProcessWeightsReqInput、PauseGenerationReqInput 等）无法单独抽出，需要 Miles 团队配合拆分，最终因长期无进展被 bot 自动关闭。

Miles fork 上生产验证过的核心逻辑（post_process_weights 服务端）
# restore: runtime format → checkpoint format
for _, module in model.named_modules():
    quant_method = getattr(module, "quant_method", None)
    if quant_method and hasattr(quant_method, "restore_weights_before_loading"):
        quant_method.restore_weights_before_loading(module)

# PWAL: checkpoint format → runtime format
for _, module in model.named_modules():
    quant_method = getattr(module, "quant_method", None)
    if quant_method and hasattr(quant_method, "process_weights_after_loading"):
        quant_method.process_weights_after_loading(module)
对我们的启示：restore → load → PWAL 与我们的 start/load/finish 完全对应，且已被 Miles 生产验证——但上游化停滞了，经验困在 fork 里，主线的 RL 裸通道至今没有这套后处理（wNa16 的 restore 零件已上岸、无调用点）。"weight update 的后处理契约"在两个生态的主线都是空缺：我们在 vLLM 把 refresh_derived_state 契约先落地，就是这个方向的第一个主线实现。

次要 · RFC 2：load_weights 与 completeness check 分离

sgl#28585 OPEN · 已收录进 #31783 §1.2

问题：很多模型的 load_weights() 既加载 tensor 又检查完整性。RL update 分 bucket 发送，第一个 bucket 就触发 "missing weights"（DeepSeek-V3 MTP 的层数检查是典型）。方案：load_weights 只加载并返回 loaded names，completeness 在所有 bucket 发完后由外部统一检查。

对我们的启示：这就是 manifest_check（我们的 follow-up scope，不在本轮）。vLLM #49090 同思路——三个项目独立收敛。
