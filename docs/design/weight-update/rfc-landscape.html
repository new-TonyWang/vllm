当前方案 · 已踩的坑 · 正在推进的 RFC · 对我们设计的启示

SGLang 生态怎么做 Weight Update：Miles 是正式答案

回答"SGLang 做不做 PWAL"必须先分清两层：主线的裸 RL 通道（veRL 等外部框架在用）和 Miles——SGLang 官方唯一指定的 RL 框架。两者行为相反。生态的正式流程是 Miles 的：update 后无条件全量重跑 PWAL，restore 按需前置。（以下全部按 2026-08 源码逐路径核实。）

Miles 流程（生态正式路径）

1 restore（条件性） — 仅当 quant_method 为 compressed-tensors（int4/fp4，PWAL 会破坏 checkpoint shape）时，先发 restore_weights_before_load RPC：resize_ 回 checkpoint shape
2 trainer 侧转换（eager） — convert_to_hf 管道：去 vocab padding → megatron→HF 布局/命名 → quantize_params 在线量化到 checkpoint 格式（fp8 blockwise / mxfp8 / nvfp4 / int4 四个 quantizer，fp8 的直接 import sglang 的 ue8m0 helper 对齐 scale 格式）
3 传输 + copy — 走 update_weights_from_distributed；engine 侧 weight_loader 只做 TP shard + copy_，零变换
4 finish — post_process_weights(post_process_quantization=True) RPC = 重跑 PWAL，无条件、全模型扫（Miles 注释原话："should always be invoked after weight updating"）；p2p/RDMA 路径额外带 post_load_weights=True 显式触发 MLA 派生（常规路径 load_weights 尾部自带）
划线原则一句话：checkpoint 格式是分界面。传输线上跑的、copy_ 进 param 的，永远是 checkpoint 格式；kernel/runtime 格式的生成永远留在 finish（PWAL）。量化可以 eager——甚至提前到 trainer 侧——因为量化的目标是 checkpoint 格式而不是 kernel 格式。破坏 checkpoint 格式的层（int4）在 load 前先 restore。

主线里已有我们契约三条的"民间版本"

DeepSeek 系的派生状态刷新（post_load_weights，挂在 load_weights 尾部）已经自发长出了三个机制，与 refresh_derived_state 的三条契约一一对应——但都是局部惯例，没有契约地位：

  • In-place：bind_or_assign(target, source)——target 存在就 copy_（保 data_ptr），不存在才赋值。就是我们的 prefer_copy
  • 增量：RL update 时传入本次到达的 weight_names，只重算出现了 kv_b_proj 的层
  • 幂等（反面教材）：首次 derive 就地把 scale 转成 ue8m0 格式（破坏输入），二次跑必须先 inverse_transform_scale_ue8m0 逆变换——代码注释明说是为 RL 多次加载打的补丁。没有"输入必须是 checkpoint 格式"的契约，就只能在 derive 里塞逆变换
  • 另：wNa16 的 restore_weights_before_loading 已上岸主线，但主线零调用点——RFC 1 上游化停滞的实物证据：零件进了，编排器没进
对我们的启示：Miles 的划线与我们完全一致——eager 只搬 checkpoint 格式，格式转换与派生刷新全在 finish。差别只在 finish 怎么跑：Miles 无条件全量重跑，它跑得起（Triton/marlin 的 PWAL 幂等可重入，restore 兜住 int4）；vLLM 抄不起——DEEPGEMM/FLASHINFER/TRTLLM 后端的 PWAL 有真实开销且重建 kernel 对象，无条件重跑正是 #50074/#49695 的病源。refresh_derived_state = Miles 的分界线 + 契约化的选择性增量（no-op 层 return、in-place 保 data_ptr、kernel 只建一次）。小彩蛋：trainer 侧 _cached_tensors（q_a/kv_a 凑对才发）与 engine 侧 cached_a_proj 是同一个"到达缓冲"手法的两端——小融合可以 eager+缓冲，MoE w13 级的大融合老实放 finish。

SGLang 已踩的坑

这些 bug 和我们要解决的问题完全相同，是 weight update 领域的"共同考试题"。

sgl#26032 PWAL 改 shape 后 weight update crash
场景：NPU 上跑 MoE 模型。冷启动时 PWAL 把 weight transpose 了（改了 shape）。RL weight update 时 trainer 发原始 shape 的 tensor，load_weights 按原始 shape 计算 shard offset → offset 越界 → crash。

根因：PWAL 永久改了 runtime param 的 shape，但 weight_loader 不知道。没人 restore 回 checkpoint shape。

教训：有 layout 转换的层，必须 restore → load → PWAL。不能 "直接 copy_ 进 runtime shape 的 param"。
sgl#27718 MTP draft weights 永远不更新
场景：DeepSeek-V3 用 MTP（multi-token prediction）做 speculative decoding。weight update 只更新 main model，draft model 的 NCCL group 从未建立。

教训：manifest_check 能发现这类遗漏——draft weights 会出现在 "expected but missing" 集合中。
sgl#33698 并发 weight update 互相覆盖
两个并发的 paused weight update 共享 completion state，互相覆盖 future。需要 session/transaction 隔离。

逐量化方法：SGLang/Miles 如何处理改 shape 的层

前面讲了 Miles 的宏观流程（条件 restore → 传输 checkpoint 格式 → 全量 PWAL）。这一节把每个改 shape 的量化方法拆开看：SGLang 到底有没有 restore？copy_ 会不会报错？PWAL 怎么兜底？

核心机制

理解 SGLang 的 restore 策略需要区分两种 weight_loader：

dense linear 的 weight_loader（default_weight_loader / row_parallel_weight_loader）：按 param 当前 shape 计算 TP shard offset。如果 PWAL 把 param 从 [N/tp, K] transpose 成了 [K, N/tp]，weight_loader 会按 [K, N/tp] 的 dim 0 大小（= K）去切 loaded_weight——shard offset 算错，TP > 1 时 assert 失败或数据写错位置。

MoE 的 weight_loader（_weight_loader_impl）：按 shard_id 语义标记（w1/w2/w3）决定 shard_dim，不依赖 param.shape。还有 is_transposed flag 可以翻转 shard_dim。而且 MoE weight_loader 内部有 maybe_restore_flashinfer_trtllm_bf16_weight_shape_for_load——遇到 TRTLLM 3D→4D 重排后的 param，先 reshape 回 3D 再 copy。

结论：MoE 的 weight_loader 对 shape 变化有内建容忍度，dense linear 没有。

结论

两层答案：

显式 restore 只有一个：wNa16 MoE（bit packing 让 param 物理变小，copy_ assert 失败）。

隐式 restore 有两个：FlashInfer TRTLLM 的 BF16 MoE 和 FP8 MoE。它们的 restore 逻辑藏在 weight_loader 内部（maybe_restore_flashinfer_trtllm_bf16_weight_shape_for_load），不是外部扩展点。

FP8 per-tensor dense 的 transpose 在 TP > 1 时确实会出错——但当前所有 RL 场景（Miles + DeepSeek 系列）都走 block FP8，不走 per-tensor 路径。这不是"没有 bug"，而是"有问题的路径没人走"。

对我们的设计意味着什么：
  • dense linear 的 weight_loader 不能容忍 shape 变化——transpose / pad 后 TP shard offset 算错。我们的 restore 扩展点（C）对 dense linear 是必须的
  • MoE 的 weight_loader 更健壮——用 shard_id 语义标记而不是 param.shape 来定 shard_dim，还有内建的 TRTLLM reshape restore。但 bit packing（Marlin INT4）仍然需要外部 restore
  • SGLang 把部分 restore 逻辑放在 weight_loader 内部是一种"就近修复"，我们的 C 扩展点把它统一提到外部是更清晰的分层

深度调研：VMM Stable VA 能替代 copy_ 吗

SGLang #33522 提出 VMM stable VA——物理页换、虚拟地址不变——作为 weight update 的长期方向。直觉上这比 copy_ 更简单：不用搬数据，直接换指针。实际分析后结论相反：在当前 NCCL 传输架构下，remap 比 copy_ 更复杂。

VMM remap 的设想

1 trainer 通过 NCCL 发来新权重 → 到达 engine GPU 显存（某个物理地址）
2 cuMemUnmap(0xABC, 旧页) → 断开 param 虚拟地址与旧物理页的映射
3 cuMemMap(0xABC, 新页) → 把同一个虚拟地址映射到新物理页
4 data_ptr() 还是 0xABC，CUDA graph 自动读到新数据

看起来省了一次 copy_。但有四个问题：

问题 1：NCCL 到达的 tensor 不是 VMM 分配的

NCCL broadcast 接收的 tensor 是 PyTorch 标准分配器（cudaMalloc）分配的。它的物理页没有 VMM handle——你不能把一个 cudaMalloc 的内存 cuMemMap 到另一个虚拟地址。

要 remap，你必须：① 用 VMM 分配新物理页 → ② 把 NCCL 数据 copy 进新物理页 → ③ 再 map 到 param 的虚拟地址。第 ② 步就是一次 copy——和直接 param.copy_(arriving_tensor) 开销一样，但多了 VMM alloc/map/unmap 的系统调用。

对比：
copy_ 方案：1 次 copy，零额外系统调用
VMM remap 方案：1 次 copy + cuMemCreate + cuMemUnmap + cuMemMap + cuMemRelease

问题 2：TP shard 不对齐 VMM 页边界

VMM 的映射粒度是 2MB 物理页。weight_loader 做 TP shard 时，从完整 tensor 里 narrow 出一个 slice 写入 fused param 的对应 offset。

fused qkv_proj 由 q/k/v 三片拼成，每片的起始 offset 不一定对齐 2MB 页边界。你不能 remap 一个 tensor 的"中间一段"——要么整个 param 一起 remap，要么不 remap。

fused qkv_proj [6144, 4096] (BF16 = 48MB)
┌─────────────────┬────────────┬────────────┐
│  q: [4096,4096] │ k:[1024,4096] │ v:[1024,4096] │
│  offset=0       │ offset=32MB   │ offset=40MB   │
└─────────────────┴────────────┴────────────┘
   ↑ 2MB 对齐 ✓     ↑ 32MB 对齐 ✓   ↑ 40MB 对齐 ✓ (这个例子恰好对齐)

但 TP shard 后每个 rank 的 slice 更小，且 k/v 的 offset 在 shard 内不再对齐：
rank 0 的 qkv: [768, 4096] = 6MB
┌──────────┬──────────┬──────────┐
│ q:[512,4096]│ k:[128,4096]│ v:[128,4096]│
│ 4MB         │ 1MB         │ 1MB         │
└──────────┴──────────┴──────────┘
  ↑ 对齐     ↑ 4MB, 对齐   ↑ 5MB, 不对齐 2MB 页！

问题 3：MoE 的 512 次 weight_loader 调用

fused w13_weight 的 shape 是 [num_experts, 2*intermediate, hidden]。每个 expert 的 w1 和 w3 单独到达，由 weight_loader 路由到 fused param 的对应 slice。256 experts × 2 projections = 512 次 weight_loader 调用，每次写 param 的一小片。

用 remap：你需要在 512 次调用中把每片数据拼进一组连续的 VMM 物理页，最后一片到了才能 remap 整个 param。本质上就是自己管理一个 staging buffer——和 copy_ 进已有 param 相比，多了 VMM 页管理，没有任何简化。

问题 4：三个扩展点仍然全部需要

即使用 VMM remap：⑤ 类层的 restore（布局恢复）还是要做，⑥ 类的派生状态还是要重算。remap 只替代了 copy_ 这一步，但 copy_ 本身不是瓶颈——瓶颈是变换逻辑（格式转换 + 派生计算），不是搬运。

唯一 remap 真正简单的场景

权重已经在 VMM 页里，按正确的 TP shard + fused 布局排好了。这意味着：

  • 一个常驻 daemon 持有后处理过的权重，存在 VMM 物理页里
  • engine 直接把自己的虚拟地址 remap 到 daemon 的物理页
  • 零拷贝，零变换——daemon 已经做完了 TP shard + PWAL

这就是 SGLang #33522 的 daemon 方案。但前提是整个权重交付管道都用 VMM：trainer → daemon → engine 全程 VMM 页，当前 RL 框架（veRL/OpenRLHF/Miles）都是 NCCL broadcast raw tensor，做不到。

vLLM 已有 VMM 基础设施

vLLM 的 CuMemAllocator（vllm/device_allocator/cumem.py）已经实现了 VMM allocator——这是 sleep mode 的基础。它的 sleep()/wake_up() 就是 unmap/remap 物理页，虚拟地址不变。

分配时:  cuMemAddressReserve(VA=0xABC) → cuMemCreate(物理页) → cuMemMap(0xABC, 页)
sleep:   cuMemUnmap(0xABC) → cuMemRelease(页)   # VA 保留，物理页释放
wake:    cuMemCreate(新页) → cuMemMap(0xABC, 新页)  # 同一个 VA，新物理页

但 sleep mode 是给整个模型做 offload 用的（按 memory pool tag 批量操作），不是 per-param 粒度。要用于 weight update 需要改造为 per-param VMM handle 管理。

结论：VMM remap 在"NCCL 接收 checkpoint 格式 tensor"的场景下不比 copy_ 简单——数据仍需搬运一次（NCCL buffer → VMM 页），还多了 VMM handle 管理和页对齐约束。它的真正价值在 daemon 预处理 + zero-copy 交付，这是一个不同的传输架构。我们 v1 用 copy_（portable、零依赖），留 VMM 作为 follow-up 的传输层优化——vLLM 已有 CuMemAllocator 基础设施，未来可扩展。

关键约束：PyTorch 的 expandable_segments（内部也用 VMM）与 pluggable allocator 互斥（pytorch/pytorch#147851）。vLLM 在使用 cumem pool 时已显式禁用 expandable_segments。
