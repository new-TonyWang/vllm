CUDA Graph 权重更新与 Refit 机制

vLLM 如何在不重新捕获 CUDA graph 的前提下完成模型权重热更新——原理、CUDA 原生 API 对比、vLLM 实现路径、以及正确性约束。

基于 vllm@main 2026-08 Weight Update Correctness 项目

Graph 捕获了什么

torch.cuda.CUDAGraph 在 capture 阶段记录一条完整的 GPU kernel launch 序列。每个 kernel node 会 bake-in 它的全部参数，包括所有 tensor 的 device pointer（data_ptr()）。replay 时，GPU 严格按照相同的 kernel 序列、相同的参数、相同的地址去读写显存。

这意味着：如果一个 tensor 的内容变了但地址没变，graph replay 会自动读到新数据。如果地址变了，graph 会从旧地址读取——产生静默的正确性 bug。

核心推论

权重更新要和 CUDA graph 共存，只有两条路：保证地址不变（graph 不用动），或者更新 graph 内的地址（用 CUDA 原生 API）。

CUDA 提供的 Graph 更新 API

CUDA runtime 确实提供了正式的 graph 更新接口。核心有两个层级：

API 粒度 作用
cudaGraphExecUpdate 整图 用一个拓扑相同的新 graph 替换旧 executable graph 的全部节点参数
cudaGraphExecKernelNodeSetParams 单节点 直接修改已实例化 graph 中某个 kernel node 的参数（包括指针）

使用这些 API，即使 tensor 被重新分配到了新地址，也可以把 graph 内 bake-in 的旧指针更新为新指针，不需要重新 instantiate。约束是 graph 拓扑（节点类型、数量、依赖关系）必须保持一致。

然而 PyTorch 没有暴露这些接口。torch.cuda.CUDAGraph 只提供 capture / replay / reset，没有 node 级别的参数更新。要用就必须走底层 C API 或自行 pybind。

vLLM 的方案：地址稳定 + copy_()

vLLM 选择了更简单的路径：强制权重 tensor 的地址永远不变，用 param.data.copy_(new_data) 原地写入新数据。由于 copy_() 不改变 data_ptr()，已捕获的 CUDA graph 自动读到新权重，零额外开销。

CUDA 原生方案

地址可以变 → 用 cudaGraphExecKernelNodeSetParams 更新 graph 里的指针

vLLM 方案

强制地址不变（copy_()）→ graph 什么都不用动

为什么不用 CUDA 原生 API

  1. 1 节点遍历成本高。piecewise 模式下一个 forward 捕获几十个子 graph，每个 graph 内部有大量 kernel node，逐个定位哪些 node 引用了哪些权重指针非常复杂。
  2. 2 PyTorch 未暴露接口。torch.cuda.CUDAGraph 没有 node-level 的参数更新 API，使用 CUDA C API 需要额外 pybind 绑定和维护负担。
  3. 3 copy_() 已经足够。通过 layerwise reload 机制可以完全控制内存分配，保证地址稳定，所以没有必要引入额外复杂度。

Layerwise Reload：如何保证地址稳定

地址稳定不是自动的——需要一套精心设计的 reload 编排来强制执行。核心流程在 layerwise.py 中：

  1. 1 initialize_layerwise_reload(model)
    遍历每层，保存当前 parameter 和 buffer 的原始引用（kernel_tensors）。这些对象的 data_ptr() 就是 CUDA graph 里 bake-in 的地址。然后将 layer 移到 meta device，释放临时空间给新权重加载用。
  2. 2 model.load_weights(iterator)
    新权重从 checkpoint 加载到临时 tensor 中。此时 layer 上的参数是 meta tensor，不占显存。
  3. 3 finalize_layerwise_reload(model)
    逐层调用 _copy_and_restore_kernel_tensors()：把处理好的新权重数据通过 param.data.copy_() 写回到第 1 步保存的原始 tensor 中，然后把原始 parameter 对象重新注册到 module 上。     
# layerwise.py:392-408 — 核心 copy-back
def _copy_and_restore_kernel_tensors(layer, info):
    parameters, buffers = info.kernel_tensors
    for name, param in parameters.items():
        param.data.copy_(getattr(layer, name))   # 原地写入
    for name, buffer in buffers.items():
        buffer.data.copy_(getattr(layer, name))  # 原地写入
    _place_kernel_tensors(layer, info)           # 重新注册原始 param

reload_weights() 在整个流程完成后不调用 clear_all_graphs()——正是因为它依赖上述机制保证了地址不变。

权重更新的两条入口

路径 触发方 入口 是否清 graph
离线 reload 用户/调度器主动触发 GPUModelRunner.reload_weights() 否
在线 weight transfer RL 训练侧推送 GPUWorker.start/update/finish_weight_update() 否

两条路径最终都走到同一个 layerwise reload 编排，通过 copy_() 保持地址稳定。clear_all_graphs() 只在 shutdown()（分布式 teardown 前）和 graph profiling 估算后调用。

地址预分配模式

部分模块在初始化阶段就预分配了稳定地址的 tensor，而不是等 process_weights_after_loading() 阶段再创建。典型案例是 HPC RoPE+Norm 融合层： 

# hpc/rope_norm.py:152-154
# Pre-allocate norm weight tensors as Parameters so they
# have stable addresses for CUDA Graph replay.
# process_weights_after_loading() updates them inplace
# via copy_() so refit does not invalidate captured
# graph tensor pointers.
self.qnorm_weight = torch.nn.Parameter(
    torch.empty(head_dim, dtype=torch.float32),
    requires_grad=False,
)

这类预分配确保了即使权重经过 quantization、repacking 等变换，copy_() 的目标地址在模型生命周期内保持恒定。

正确性风险

核心不变量

权重 tensor 的 data_ptr() 在 reload 前后必须不变。如果任何环节创建了新 tensor（新地址）而不是 copy_() 进旧 tensor，CUDA graph replay 会从旧地址读取 stale data——这是一个静默正确性 bug，不会有任何报错。

已知的破坏场景：

场景 原因 后果
量化方案改变 dtype/shape copy_() 要求 shape 和 dtype 兼容，无法原地写入 需要 fallback 到 clear_all_graphs() 重新捕获
PWAL 中 replace_parameter 直接替换 module 上的 parameter 对象，新 tensor 地址不同 graph 读到旧权重或无效内存
process_weights_after_loading 分配新 buffer 部分层的后处理创建新 tensor 而非原地更新 graph 读到旧权重或无效内存
Sleep/Wake 后地址漂移 CuMemAllocator 在 wake 时可能分配到不同地址 需要 graph 重新捕获（由 sleep/wake 流程处理）
