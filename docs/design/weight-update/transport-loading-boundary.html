传输与加载的边界

Weight update 的四种传输引擎如何交付权重，和 model.load_weights() 之间有什么耦合

总览

传输引擎交付什么调用 load_weights？与加载的耦合
NCCL broadcast checkpoint 格式 (name, tensor) 直接调 解耦
CUDA IPC checkpoint 格式 (name, tensor) 直接调 解耦
Sparse NCCL checkpoint 坐标 (name, indices, values) 展开为 NaN-masked checkpoint tensor 后调 load_weights 解耦（#53751 重写）
Sharded RDT 按需拉取的 checkpoint 切片 init 时用 FakeTensor 录制 plan，replay 时不调 部分耦合
我们的设计从 model.load_weights([(name, tensor)]) 开始。传输层负责把 checkpoint 格式的 (name, tensor) 送到这个接口。怎么送的（broadcast / IPC / pull / M2N）不影响 weight_loader 包装和 refresh_derived_state 的逻辑。

逐引擎分析

NCCL Broadcast 完全解耦

Trainer broadcast 完整的 checkpoint 格式 tensor（HF named_parameters() 的 name + 对应 tensor）。Engine 每收到一个就调一次 model.load_weights([(name, weight)])。

# nccl_engine.py:213-221 — 逐 tensor 接收
for name, dtype_name, shape in zip(...):
    weight = torch.empty(shape, dtype=dtype, device=self.device)
    self.model_update_group.broadcast(weight, src=0)
    self.model.load_weights([(name, weight)])   # ← 标准接口
    del weight

与加载的关系：零耦合。传输层只管 broadcast + 拼出 (name, tensor)。name 是 checkpoint name（如 model.layers.0.mlp.gate_proj.weight），tensor 是完整的未分片 checkpoint tensor。load_weights 内部的 weight_loader 负责 TP narrow、expert routing、fused param 拼接。

packed 模式：多个 tensor 打包进一个 buffer 一起 broadcast，减少通信次数。解包后仍然是 (name, tensor) 列表，调同一个 load_weights。打包是传输优化，不影响加载逻辑。

CUDA IPC 完全解耦

Trainer 把 tensor 放在 GPU 上，通过 IPC handle 让 engine 直接访问。Engine 用 rebuild_cuda_tensor 拿到 tensor 后，一样调 model.load_weights(weights)。

# ipc_engine.py:246-247
with disable_mtp_completeness_check():
    self.model.load_weights(weights)   # ← 同一个接口

与加载的关系：和 NCCL 完全一样——传输层交付 (name, tensor)，加载层消费它。传输方式从网络 broadcast 变成共享内存访问，但接口不变。

Sparse NCCL 解耦 （#53751 重写后）

只传变化的部分：一组 (name, indices, values)，使用 checkpoint 坐标（不是 runtime 坐标）。

关键机制：把 sparse patch 展开为完整 checkpoint shape 的 tensor，未改位置填 NaN。然后 monkey-patch copy_ 让 NaN 位置保留原值，最后走标准 model.load_weights()。

# checkpoint_weight_patch.py — 核心逻辑
# 1. sparse → 完整 checkpoint tensor（NaN = 不改）
flat = torch.full((numel,), float("nan"), dtype=patch.dtype)
flat.index_copy_(0, patch.indices, patch.values)
checkpoint_tensor = flat.view(patch.shape)

# 2. monkey-patch copy_ 保留 NaN 位置的原值
def copy_non_nan_(dst, src):
    return torch.where(torch.isnan(src), dst, src, out=dst)

# 3. 走标准 load_weights → weight_loader 做 TP narrow / routing
model.load_weights([(name, checkpoint_tensor)])

与加载的关系：和 NCCL / IPC 一样走 model.load_weights()。TP narrow、expert routing、stacked_params_mapping 全部复用。Checkpoint name → param 的映射由 model loader 处理，传输层不需要知道 runtime layout。

限制：sparse-loader contract 要求最终写入必须是 same-shaped floating-point copy_。不支持 composed loader、multi-stage loader、custom-write 路径。Start/finish 仍是 no-op（sparse patch 只修改已存在的值，不触发 shape 变化或派生状态刷新）。

和我们设计的关系：Sparse NCCL 是 delta update（只改部分元素），我们的设计是 full reload（全量替换）。两者互补而非冲突——sparse 适合 LoRA delta 和微调，full reload 适合 RL weight update。Sparse 走 load_weights 意味着 weight_loader 包装（在线量化）理论上也能覆盖它，但 NaN-masked copy_ 的 monkey-patch 需要和量化包装的 dtype 转换兼容。
Sharded RDT 部分耦合

Ray Direct Transport。和前三种引擎的根本区别：不是 trainer push，而是 engine pull。Engine 主动从 trainer 拉取本 rank 需要的那一片数据。

背景：为什么要 pull？

NCCL broadcast 模式下，trainer 把完整 checkpoint tensor broadcast 给所有 rank，每个 rank 的 weight_loader 再 narrow 出自己需要的 shard。这意味着每个 rank 都收了完整数据但只用一部分——TP=8 时，7/8 的传输是浪费。

RDT 的思路：让每个 rank 只拉自己需要的那一片。但要做到这一点，engine 必须提前知道"我这个 rank 需要 checkpoint tensor X 的哪一段"。这个信息不是写在配置文件里的——它是 weight_loader 代码在运行时算出来的（比如 TP rank 2 需要第 2048~3072 行）。所以 RDT 需要"试跑一次"weight_loader 来把这些切片信息提取出来。

BAKE：录制购物清单（一次性）

init 时，engine 做一次模拟加载来"偷看" weight_loader 会怎么切数据：

# 简化版 BAKE 流程
fake_weights = [(name, FakeRDTTensor(name, shape, dtype)) for name, shape, dtype in trainer_metadata]
model.load_weights(fake_weights)   # ← 假装在加载

FakeRDTTensor 是零存储的占位 tensor。当 weight_loader 对它做 narrow(dim=0, start=1024, length=1024) 然后 copy_ 到 param 时，FakeRDTTensor 不真的搬数据，而是记录这个操作："从 checkpoint tensor X 的第 1024 行开始取 1024 行，写到 param Y 的某个位置"。

所有 param 录完后，产出一个 plan——本 rank 需要从 trainer 拉哪些 slice，每个 slice 写到哪个 param 的哪个 offset。Plan 在 init 时定死，后续所有 weight update 都按同一个 plan 执行。

REPLAY：按清单拉货（每次 weight update）

Plan 定好后，每次 weight update 不再调 model.load_weights()。流程变成：

# 简化版 REPLAY 流程
for chunk in plan.chunks:
    slices = pull_from_trainer(chunk.keys)   # 只拉本 rank 需要的 slice
    for slice, target in zip(slices, chunk.scatters):
        target.param.data[target.offset:...].copy_(slice)   # 按 plan 直接写

不走 weight_loader（它的 narrow 逻辑已经 bake 进 plan 里了），不走 model.load_weights()。

当前的问题：被 layerwise 拖累

BAKE + REPLAY 本身是一个很好的优化——只拉需要的 slice，省了大量带宽。但 RDT 在拿到 slice 之后的处理，完全绑定在 layerwise reload 上。这给它加了三层不必要的复杂度：

第一层：清空再重建。start 时把所有 param 放到 meta device（一种"假设备"，表示 tensor 存在但没有实际数据）。GPU 上的 param 数据被丢弃。然后 REPLAY 时逐层 materialize（重新在 GPU 上分配内存），再把拉来的 slice 写进去。

第二层：layerwise buffer。因为 param 被清空了，需要一个临时 buffer 来接收数据，然后搬到新分配的 param 里。这就是 layerwise buffer——为了清空再重建而存在的中间暂存区。

第三层：重跑 PWAL。finish 时调 finalize_layerwise_reload，对所有层重跑 PWAL 做格式转换。但第四章已经论证了为什么不应该重跑 PWAL（幂等性问题、destructive fusion 累乘、kernel 重建等）。

当前 RDT 流程（六步）：
  start  → 把 param 放到 meta device（清空 GPU）
  replay → 分配接收 buffer
         → 拉 slice 到 buffer
         → materialize param（重新分配 GPU 内存）
         → scatter（从 buffer 搬到 param）
  finish → 跑 PWAL

用我们的方案：去掉三层，只剩核心

如果 param 始终在 GPU 上（不清空），REPLAY 拉来的 slice 可以直接 copy_ 进已有的 param——不需要 meta device、不需要 materialize、不需要 layerwise buffer：

改造后 RDT 流程（三步）：
  start  → 只对 ⑤ 类做 restore（param 留在 GPU 上）
  replay → 拉 slice → copy_ 进已有 param（一步完成）
  finish → refresh_derived_state

Plan 完全不变——BAKE 录制的"从 trainer 拉哪一片、写到 param 的哪个 offset"信息照用。只是执行方式从"清空→重建→搬运"变成"原地覆盖"。

环节RDT 当前（六步）改造后（三步）省掉了什么
startparam → meta device（清空）只对 ⑤ 类 restoremeta device + 全量清空
replay分配 buffer → 拉 slice → materialize → scatter拉 slice → copy_buffer 分配 + materialize + scatter
finishfinalize_layerwise_reload（跑 PWAL）refresh_derived_statePWAL 重跑 + 其带来的所有幂等性问题
结论：RDT 的核心价值（BAKE plan + 按需拉取）和我们的设计完全兼容。被 layerwise 绑定是历史原因——当时 weight update 只有 layerwise 一种后处理方式。去掉 layerwise 依赖后，RDT 反而变得更简洁：六步变三步，不需要 meta device、不需要 layerwise buffer、不需要重跑 PWAL。这是 RDT 引擎自己的改造，不影响我们的核心设计（refresh_derived_state + weight_loader 包装）。

NCCL M2N（#51520，Open）

M2N 是 NCCL broadcast 的演进：trainer TP=X，inference TP=Y，通过 nccl-extensions 做跨 mesh resharding。Trainer 不需要 materialize 完整 tensor——直接发送本地 shard。

当前实现有两条路径：

  • Direct：resharding 后直接写入本 rank 的 param storage（跳过 load_weights）—— follow-up 阶段
  • Fallback（当前主要路径）：收完整 tensor 后走 model.load_weights([(name, buffer)])——和 broadcast 行为一致

有 fallback 条目时走 layerwise reload lifecycle（start/finish_weight_update）；全部 direct 时 start/finish 是 no-op。

在线量化包装可用？直接可用fallback：可用；direct：需要额外 hook需要改 plan 或在 plan 之外加 hook

架构边界

传输层 加载层 ───────── ───── IPC ──────┐ ┌─ weight_loader (TP narrow + copy_) │ │ NCCL ─────┤ (name, tensor) ├─ weight_loader 包装 (在线量化) │ checkpoint 格式 │ Sparse ───┤ (NaN-masked tensor) ├─ refresh_derived_state (finish) │ │ M2N ──────┘ └─ NaN-masked copy_ (sparse delta) ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ RDT ──────── BAKE 录制 plan ──── REPLAY 直接写（吸收了加载层）

上半部分（IPC / NCCL / Sparse / M2N）都走 model.load_weights()：传输层交付 checkpoint 格式的 (name, tensor)，加载层消费。Sparse NCCL 经 #53751 重写后也走这条路（通过 NaN-masked checkpoint tensor）。我们的 weight_loader 包装和 refresh_derived_state 对这四种引擎完全适用。

下半部分（RDT）吸收了 weight_loader 的 narrow 逻辑：

  • BAKE 时录制 plan，REPLAY 时不调 load_weights，按 plan 直接写
  • 如果要支持在线量化，需要在 BAKE plan 中加入量化 hook，或在 REPLAY 后走 refresh_derived_state（当前走 finalize_layerwise_reload，改为我们的 finish 逻辑即可）

结论

Weight update 的传输和加载是两层问题。传输层解决"tensor 怎么到达 engine"，加载层解决"到达的 tensor 怎么写进 param"。

对于主流引擎（NCCL / IPC），两层完全解耦——我们的设计不需要关心传输方式。对于 RDT 和未来的 M2N，传输层"吸收"了部分加载逻辑（TP narrow），但这个耦合在我们的包装层之前——weight_loader 包装处理的是 narrow 之后的数据，不受影响。

Finish 的触发也不是加载层判断的——是 trainer 调 finish_weight_update() RPC。Trainer 知道自己发了多少权重，发完了就调 finish。Engine 不需要自己判断"到齐了没有"。
